# design.md — 统一多产品账号体系并接入 Qoder

关联需求见 `prd.md`。本文只写技术设计与取舍。

## 1. 决策记录（所有者已回答）

### D1 同名模型路由：**两产品都参与，按成本与到期时间加权**

所有者原话：「平均路由，都参与，按照成本与到期时间」。

**重大发现：这套机制在 pool 里已经存在。** 不必新造。

`go-gateway/internal/pool/pool.go:10-21` 记录的现有两级策略：

```
挑选策略（两级）：
 1. 到期分层：先按「最近到期积分」的到期日把 healthy 候选分组，
    只保留最早到期的一档 —— 优先消耗快过期的额度，避免积分作废；
    到期日未知的账号排最后。
 2. 档内挑选：同档账号按「闲置补偿 + 成功率」加权取 Top5，再加权随机抽签，
    即同一天到期的账号平均分摊。
```

`weightOf`（pool.go:1270）已含 credits 比例因子（×10）。

⇒ **D1 的实施不是"新增路由算法"，而是"把产品维度接进已有的候选池"。**
候选集从「一个产品的账号」变成「两个产品的账号」，其余策略逐字复用。
这是本次迁移风险最低的一条路径，也最符合所有者「功能和代码没有太大的偏移」的要求。

### D2 命名：**XX账号** 格式（所有者已赞同）

侧边栏：WorkBuddy 账号 / Qoder 账号 / Trae 账号 / 豆包账号。路由 `/` 不变。

### D3 provider 统一：可以做，但必须零偏移（所有者已赞同，附硬约束）

「可以进行统一，但是必须在开发阶段完整调试好 确保功能和代码没有太大的偏移」

### D4 两种凭证来源都要支持（所有者明确要求）

方式 A 软件内 OAuth 登录 + 方式 B 导入已有 auths。

## 2. 产品抽象的边界（关键取舍）

### 2.1 抽什么、不抽什么

**抽象的是"数据与生命周期"，不是"全部业务逻辑"。**

| 层 | 是否抽象 | 理由 |
|---|---|---|
| 账号凭证的加载/落盘/刷新 | ✅ 抽象 | 两产品形态不同但语义一致（有 token、会过期、需 refresh） |
| 额度与到期查询 | ✅ 抽象 | 两产品都有 total/remaining 与某种到期语义 |
| 模型列表与能力 | ✅ 抽象 | 两产品都产出「模型名 + 能力」 |
| 登录流程 | ✅ 抽象为「发起 / 轮询」两步 | 两产品都是 device flow |
| **选号与冷却** | ❌ **不复用抽象** | 见下 |
| **签到/养号等任务** | ❌ 不进本任务 | 见 prd Out of Scope |

### 2.2 为什么选号**不**做成 provider 方法

选号是**跨产品**的决策（「这次用谁的号」），而 provider 是**产品内**的实现。
若把它塞进 provider，就会变成"每个产品自己挑自己的号"，跨产品加权无从谈起。

因此边界是：

```
provider（产品内）   →  暴露「这个产品有哪些可用账号 + 它们的成本/到期」
pool（跨产品）       →  拿全部产品的候选，统一按到期分层 + 加权随机挑
```

这正是现有 pool 的形状 —— 它本来就是"拿一批账号，按到期与权重挑一个"。
**产品维度只需在候选集的来源上加一层，挑选逻辑零改动。**

### 2.3 成本的跨产品可比性（必须解决的硬问题）

**先记一个反直觉的实测事实**：现有策略里，"成本"因子并非在所有路径都生效。

| 路径 | 触发条件 | 是否用 credits |
|---|---|---|
| `weightOf`（三因子） | `tiered=false`，即**所有账号都无到期信息** | ✅ credits 比例 ×10 |
| `tierWeightOf`（同档内） | `tiered=true`，即有账号带到期信息 | ❌ **不含 credits** |

`pool.go:1237` 写明了原因，而且理由是对的：

> 同一到期档意味着这些额度的「紧迫度相同」，按积分多少分配会让高积分账号
> 长期吃掉大部分流量，同档内就不再是平均使用。

**这意味着**：若把两产品直接合并进同一个候选池，只要**有任何**账号带到期
信息（现实中必然如此），`tiered=true`，**credits 就会被丢掉** ——
所有者要的"按成本"就落空了。这正是"想当然复用"会踩的坑。

#### 因此成本必须**另立一个跨产品维度**，而不是复用 credits 项

两产品的"成本"单位不同（WorkBuddy 积分 ≠ Qoder 积分），绝对值不可比：

| 产品 | 额度字段 | 成本字段 |
|---|---|---|
| WorkBuddy | `total` / `remaining`（积分） | `CreditMultiplier`（模型级倍率） |
| Qoder | `userQuota.total/remaining` + `addOnQuota` | `PriceFactor`（模型级倍率） |

**方案：把「成本」定义为跨产品可比的"单位额度消耗率"，作为 tierWeightOf 的
一个新乘子**（而不是塞回 credits 项）：

```
消耗率 cost = 1 / (该模型在本产品的成本倍率)        // 倍率越大 → 越贵 → 权重越小
           倍率缺失（nil）时 = 1（中性，不猜测）
```

这样：
- 保留"同档内平均分摊"的既有目标（闲置 + 成功率仍是主项）；
- 成本作为**小幅乘子**区分"同样紧迫、但一个更贵"的两个产品；
- 倍率三态语义不变：未声明 → 中性 1，而不是当 0（当 0 会被永久冷落）。

**量级必须显式校准**：现有 `weightOf` 里 credits 项是 ×10 的大项，
而这里成本只是微调。设计上刻意做成小乘子（1.0 附近），避免成本压过
"同档平均分摊"这一更重要的目标 —— 后者关系的是一旦过期就净损失的额度。

**这个校准值必须实测确定，不能拍脑袋**：C5 的验收要求是"两产品都被路由到、
且贵的一方份额更低"，因此实现时用一个可注入的权重参数 + 单测断言份额比例，
而不是把魔数硬编码进去。

### 2.4 到期时间的跨产品可比性

| 产品 | 到期字段 | 来源 |
|---|---|---|
| WorkBuddy | `SoonestExpireAt`（最近到期积分） | 已有，持久化在 state.json |
| Qoder | `rewardExpiresAt`（签到奖励到期） | 参考实现 `CheckinStatus` 已解出 |

两者语义**不完全相同**（一个是积分包到期，一个是签到奖励到期），但都是
"这个账号的额度快作废了"的信号。**用它做分层是合理的**，但要在界面上
如实标注各自的口径，不能让用户以为两者是同一个东西。

**若某产品拿不到到期时间**（Qoder 未登录时必然拿不到）：该产品的账号
排到"到期未知"那一档 —— 现有策略已定义了这一档的行为（排最后），
无需新规则。

## 3. 数据分层与迁移

```
~/.wb-switch/
├── accounts.json              ← 保持不动（WorkBuddy 现有，20 条）
├── qoder/
│   └── accounts.json          ← 新增
└── gateway/gateway_auths/
    ├── workbuddy-<uid>.json   ← 现有（19 个）
    └── qoder-<uid>.json       ← 新增
```

**兼容性约束**：`accounts.json` 的**路径与格式一个字都不改** ——
它是所有者现有数据的载体，动了就有丢数据的风险。Qoder 用新目录。

网关侧 `auth.LoadDir` 现按前缀匹配；新增 Qoder 前缀后需要区分产品。
**改动点集中在加载层，选号逻辑不变**（见 2.2）。

## 4. Qoder 实现要点（来自实测）

### 4.1 签名层（已验证有效）

```
cosy-key = base64(RSA_PKCS1v15(临时 AES 密钥))
info     = base64(AES-128-CBC(身份 JSON, key=iv=临时密钥))
签名      = MD5(payloadB64 + "\n" + cosyKey + "\n" + date + "\n" + body + "\n" + pathSig)
Authorization: Bearer COSY.<payloadB64>.<签名>
```

**四个必须照抄的细节**（改任何一个都会 101 Signature invalid，实测）：

1. 临时密钥是 **16 个 ASCII 字符**（`hex[:16]`），不是 16 个随机字节；
2. 身份 JSON 必须**按 key 排序 + 无空白**序列化；
3. 签名里的 `pathSig` 是 URL path **去掉 `/algo` 前缀**；
4. GET 请求 body 用**空串**签名，不是 `"{}"`（参考实现注释明确警告过）。

### 4.2 双区（参考实现没有，是我们新增的）

| | 国服 | 国际版 |
|---|---|---|
| 授权页 | `qoder.com.cn` | **`qoder.com`** |
| openapi | `openapi.qoder.com.cn` | `openapi.qoder.sh` |
| gateway | `gateway.qoder.com.cn` | `api3.qoder.sh` |

实测同一个 `client_id` 在两区都有效（都 302 进登录页）⇒ 域名做配置项即可。

### 4.3 上游端点

| 用途 | 端点 |
|---|---|
| 模型列表 | `GET /algo/api/v2/model/list?Encode=1` |
| 对话 | `POST /algo/api/v2/service/pro/sse/agent_chat_generation?...` |
| 额度 | `GET /api/v2/quota/usage` |
| 套餐 | `GET /api/v2/user/plan` |
| 用户信息 | `GET /api/v1/userinfo` |
| 签到状态 | `GET /sash/api/v1/me/daily-check-in/status` |
| token 刷新 | `POST /api/v1/deviceToken/refresh` |

注意：模型列表与对话走 **gateway**（需 COSY 签名）；额度/套餐/userinfo 走
**openapi**（参考实现里是普通 `Bearer dt-`，**不签名**）。两条路径的鉴权方式不同。

## 5. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 重构破坏 WorkBuddy 行为 | 逐字不改 `accounts.json` 路径与格式；重构前后用同 fixture 跑同批用例比对；每个子任务独立可回滚 |
| Qoder 签名未来失效 | 签名层独立成模块 + 已有可复跑的探测脚本（`uitest/probe-qoder-signature-control.cjs`），失效时能立刻定位到是签名层而非业务层 |
| 跨产品权重导致某产品被饿死 | 保留"该产品无可用账号则用另一个"的回退；并在界面上显示实际命中的产品 |
| 两产品积分口径不同被误读 | 界面分别显示各自口径，不做假的"总积分" |

**回滚点**：每个子任务一个提交，`accounts.json` 与现有网关行为在 C1/C2 后
应完全不变 —— 此时回滚 C3 及以后即可回到单产品状态。

## 6. 子任务拆分与依赖

```
C1 命名统一（纯前端文案，零逻辑）
     ↓
C2 provider 抽象（WorkBuddy 搬入，行为逐字不变）
     ↓
C3 Qoder 后端（签名 + 双区 + 登录两方式）
     ↓
C4 Qoder 账号页（复用现有卡片组件）
     ↓
C5 网关多产品路由（把产品维度接进已存在的到期分层 + 加权策略）
     ↓
C6 全流程真实账号实测（端到端验收，允许真实账号）
```

C1 可立即做且独立验收。C2 是地基。C5 依赖 C3。**C6 是最后的端到端验收门**，
不通过则整体不算完成 —— 它验的是"真实链路"，mock 与单测都替代不了。

## 7. 为什么必须有 C6（真实账号实测）

本任务有四处**只有真实链路才能验证**的地方，这正是所有者要求它的原因：

| 盲区 | 为什么 mock 验不到 |
|---|---|
| COSY 签名是否被接受 | mock 里我们自己签自己验，永远"通过"；只有真上游会回 101 |
| 真实额度/到期字段名 | 参考实现的字段名是从别处逆向来的，上游可能已改；只有真响应能确认 |
| 真实流式格式 | Qoder 是嵌套 SSE（`FetchKeys=llm_model_result`），与标准 OpenAI 流不同，需要真解析一次 |
| 跨产品路由的真实分布 | 单测里账号是我们造的，权重分布"看起来对"不代表真实池下不吃偏 |

第 2 条尤其重要：`design.md` §4.3 列出的端点与字段**全部来自参考实现**，
而那份实现是第三方逆向的结果 —— **它是证据，不是真理**。C6 的第 4/5 项
就是用真实响应去校验这些假设，不成立就改 `design.md` 再实现。
