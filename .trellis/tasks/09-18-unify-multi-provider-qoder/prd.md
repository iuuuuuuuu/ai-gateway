# 统一多产品账号体系并接入 Qoder

## Goal

让本软件从「WorkBuddy 单产品工具」演进为「多 AI 编码产品账号管理器」：把现有
「账号管理」按产品正名为 **WorkBuddy 账号**，新增 **Qoder 账号**，并为后续
接入更多产品建立一套**统一而不失各自特性**的 provider 架构。

用户价值：一个软件管全部 AI 编码产品的账号 —— 登录、看积分、养号、接网关，
不必为每个产品装一个工具。

## Background（已完成的证据调查）

### 证据 1：COSY 签名仍然有效（决定性，对照实验）

参考实现 `Sliverkiss/qoderwork2api` 的签名层（RSA 包裹 AES 密钥 + AES-128-CBC
加密身份 + MD5 请求签名）**经实测仍然被上游接受**。

方法：用**伪造 token** 发请求，并在「签名完好」与「签名损坏」之间做对照 ——
这样无需接触任何真实凭证即可判断签名是否被校验：

| 实验 | 响应 |
|---|---|
| A 签名完好（伪造 token） | HTTP 403 `{"code":"105","message":"Login expired"}` |
| B signature 改坏 | HTTP 403 `{"code":"101","message":"Signature invalid"}` |
| C cosy-key 改坏 | HTTP 403 `{"code":"101","message":"Signature invalid"}` |
| D info 改坏 | HTTP 403 `{"code":"105","message":"Login expired"}` |

判读：B/C 与 A/D 的响应**不同** ⇒ 上游确实在检查签名；A 过了签名关（卡在
token）⇒ 签名算法有效。

脚本：`uitest/probe-qoder-signature-control.cjs`（可复跑）。

### 证据 2：两区同构，同一个 client_id 通用

| 项 | 国服 | 国际版 |
|---|---|---|
| 授权页 | `qoder.com.cn/device/selectAccounts` | **`qoder.com`**/device/selectAccounts |
| openapi | `openapi.qoder.com.cn` | `openapi.qoder.sh` |
| gateway | `gateway.qoder.com.cn` | `api3.qoder.sh` |
| 同一 client_id `1c5e33e1-…` | 302 进登录页 ✓ | 302 进登录页 ✓ |

⇒ 两区是同一套协议，**只需把域名做成配置项**即可支持两区。

**这一条推翻了参考实现的假设**：`qoderwork2api` 只支持国服（硬编码
`qoder.com.cn`），而所有者本机装的是**国际版**（`~/.qoder/.cache/endpoint-cache.json`
实测为 `api3.qoder.sh`）。

### 证据 3：本机凭证不可直接复用

所有者已登录 Qoder IDE，凭证在
`%APPDATA%\Qoder\User\globalStorage\state.vscdb` 的 `ItemTable` 中，键为
`secret://aicoding.auth.userInfo` 等。值是可读的，但形态是
`{"type":"Buffer","data":[…]}`，字节以 `v10` 开头 + DPAPI 加密
（`Local State` 的 `os_crypt.encrypted_key` 前缀为 `DPAPI`）。

⇒ 无法在 Node/Go 侧直接解密（绑定当前 Windows 用户的 DPAPI）。
**这正说明「导入已有凭证」这条路要么走 OAuth 重新授权，要么由客户端自己解密后导出。**

### 证据 4：模型命名存在真实冲突

两产品都暴露同名模型：

| 模型名 | WorkBuddy | Qoder |
|---|---|---|
| `auto` | ✓ | ✓ |
| `deepseek-v4-pro` | ✓ | ✓ |
| `glm-5.2` | ✓ | ✓ |

⇒ 网关若同时接两产品，同名模型会撞在一起。**所有者已决定不做隔离**：
两产品都参与、按成本与到期时间路由（见 R5）。

### 证据 5：现有架构没有 provider 抽象

```
Trae   → 共用账号库，只换登录态快照（switcher 模块）
豆包    → 独立账号库 + 独立抓包凭证（doubao* 命令）
WorkBuddy → accounts.json + gateway_auths/workbuddy-*.json
```

每个产品各写一套，无统一接口。侧边栏命名也不一致：有「账号管理」「Trae 账号」
「豆包账号」三种写法。

## Requirements

### R1 命名统一（所有者明确要求）

侧边栏与页面标题统一为「**XX账号**」格式：

| 现状 | 目标 |
|---|---|
| 账号管理 | **WorkBuddy 账号** |
| Trae 账号 | Trae 账号（不变） |
| 豆包账号 | 豆包账号（不变） |
| ——（无） | **Qoder 账号**（新增） |

约束：路由 `/` 保持不变（书签与外部链接不能失效）；页面内所有指向
「账号管理」的文案（如 `CreditStatsPage` 的空态提示）同步更新。

### R2 抽 provider 层（所有者要求「可以统一」）

把「每个产品各写一套」收敛为统一接口 + 各自实现。

**硬约束（所有者原话：「必须在开发阶段完整调试好 确保功能和代码没有太大的偏移」）**：

- 重构期间 **WorkBuddy 的行为必须逐字不变** —— 现有测试全绿只是底线，
  还需逐项核对关键行为（选号、冷却、签到、养号、积分口径）。
- 不允许「为了抽象而改语义」。
- 抽象必须是**可逐产品关闭**的：某产品接不上抽象时能退回独立实现，
  而不是被抽象卡死。

### R3 接入 Qoder（两种凭证来源都要支持，所有者明确要求「两个方式都要支持」）

- **方式 A — 软件内 OAuth 登录**：PKCE Device Flow。点「登录 Qoder」→
  浏览器授权 → 自动落盘。体验与现有 WorkBuddy 登录一致。
- **方式 B — 导入已有凭证**：用户从别处（已有的 qoderwork2api auths 目录、
  或自己导出的文件）导入。

两种方式写入**同一套账号存储**，登录后行为完全一致。

### R4 支持两区（证据 2 支持，成本极低）

国服（`qoder.com.cn`）与国际版（`qoder.sh`）都要支持，域名做配置项。
默认区按用户选择，不猜。

### R5 网关同名模型路由

**所有者已决定：两产品都参与，按成本与到期时间路由。**

原话：「平均路由，都参与，按照成本与到期时间」。

`auto` / `deepseek-v4-pro` / `glm-5.2` 等同名模型，两产品的账号进入**同一个
候选池**，由既有策略决定用谁 —— 这正是所有者说的「平均路由」：

1. **到期分层** —— 优先消耗快过期的额度（避免作废）；
2. **档内平均分摊** —— 同档内加权随机；
3. **成本作为档内修正因子** —— 更便宜的更受偏好。

技术细节见 `design.md` §2.3。其中记了一个**反直觉的实测事实**：现有策略在
「同档内」**刻意丢掉了 credits 因子**（`pool.go:1237`，理由是同一档内紧迫度
相同，按积分分配会让高积分号长期吃掉流量）。因此「按成本」**不能靠复用
credits 实现** —— 这是"想当然复用"会踩的坑，必须另立跨产品可比的成本维度。

### R6 全流程真实账号实测（所有者明确要求）

原话：「最后再加一个全流程的实际测试，允许使用真实账号进行实测」。

**动机**：单元测试绿 ≠ 真实链路通。本任务跨了两个产品、两种鉴权、两套端点，
mock 覆盖不到的地方（真实签名是否被接受、真实额度字段名、真实流式格式、
跨产品路由在真实账号池下的分布）**只有真实账号能验**。

**所有者已授权使用真实账号实测。**

范围（逐项都要真实链路，不允许用 mock 充数）：

1. **登录两方式**：方式 A 浏览器授权、方式 B 导入，都跑真实流程
2. **落盘正确**：凭证文件生成、字段完整、权限正确
3. **账号页真实数据**：额度、到期、区域显示的是上游真值
4. **拉模型**：与直连上游的结果比对（不是只看"非空"）
5. **走网关真实对话**：流式 + 非流式各一次，断言内容与格式
6. **token 自动刷新**：真实触发一次 refresh（含 drt 轮换）
7. **跨产品路由实测**：同名模型连续 N 次，统计真实命中分布
8. **重启持久化**：停掉重启，账号与状态仍在
9. **WorkBuddy 回归**：真实账号跑通现有流程，行为与重构前一致
10. **清理**：不留残留进程、临时凭证、孤立数据目录

**硬约束（沿用仓库既有铁律，不得放宽）**：

- 独立实例：独立端口（5789x）+ 独立数据目录 + 独立进程名
- 凭证从正式目录**只读复制**，绝不改动原件
- **绝不**触碰所有者的 `:7864` 与 `:43120`
- 输出一律脱敏：**不得**把真实账号标识写进提交、日志、工件
- 方式 A 需要所有者**在浏览器点一次授权** —— 这是一个明确的人工交接点，
  不能用"我代点"绕过

## Out of Scope

- Qoder 的**定时签到/养号**：参考实现有（每日 9/21 点），但那是独立功能，
  等账号体系跑通后另开任务。**本任务不含**。
- Trae / 豆包 接入 provider 抽象：本任务只做命名统一，**不重构它们的内部实现**
  （避免一次改太多，违背「没有太大偏移」的要求）。
- Qoder 的积分/用量统计页：同上，另开任务。
- 从 Qoder IDE 本地凭证库解密导入（证据 3：DPAPI 绑定用户，做不到）。
  方式 B 只支持**用户自备的 auths 文件**。

## 任务拆分（父任务 + 子任务）

一个用户请求里包含多个**可独立验收**的交付物，按 Trellis 约定拆成父子任务。
父子关系不是依赖系统；真正的顺序（先 P0/P1、Qoder 在其后）写在各子任务的
`implement.md` 里。

| 子任务 | 交付物 | 可独立验收的判据 |
|---|---|---|
| C1 命名统一 | 侧边栏与页面正名为 XX账号 | 界面文案 + 路由不变 |
| C2 provider 抽象 | 抽出接口，WorkBuddy 搬入且行为逐字不变 | 重构前后同 fixture 结果逐项一致 |
| C3 Qoder 后端 | COSY 签名 + 双区 + OAuth 设备流 + 导入 | 能登录、能拉模型 |
| C4 Qoder 账号页 | 账号卡片（复用现有组件） | UI 套件覆盖 |
| C5 网关多产品路由 | 按 R5 实现：两产品同池，到期分层 + 档内分摊 + 成本修正 | 两产品模型都能调、成本与到期因子可测生效、现有调用不受影响 |
| C6 全流程真实实测 | R6 的 10 项端到端实测（真实账号） | 每项留可复跑脚本 + 脱敏输出 |

**依赖顺序**（写在子任务里，不靠父子结构表达）：C1 可先做（纯文案，零逻辑）；
C2 是 C3/C4/C5 的地基；C5 依赖 C3。
