## 1. 多应用账号与登录态切换

### 1.1 每个应用的登录态是**独立**的，切换不会互相影响

| 应用 | 登录态载体 | 切换语义 |
|---|---|---|
| WorkBuddy 客户端（国服 / 国际版） | 各区域一个固定认证文件 | 按目标账号**区域**写对应的那个文件；两区域互不干扰 |
| CodeBuddy CLI | `%USERPROFILE%\.codebuddy\settings.json` 的 `env.CODEBUDDY_AUTH_TOKEN` | 保留该文件中的**其他配置**，只改这一个键 |
| CodeBuddy CN IDE | 桌面客户端的 Safe Storage（state.vscdb 内的 secret） | 与 CodeBuddy CLI **完全独立**，两者可以各登一个账号 |
| Trae Work / Trae | 同一份账号库，**登录态快照互相独立** | 同一账号可在两个应用里分别切换，互不影响 |
| 豆包 | 多 Profile 快照 | 见 §1.4 |

**适用版本**：1.0.x 全线（本页核对于 1.0.46）。

**为什么必须分开**：三套登录态是三个不同的产品面。把它们合并成"切一次全变"
会让"我只想换 CLI 的账号"变成一次影响面不可控的操作。

### 1.2 「切换」的生效时机（最容易误判的一条）

- **WorkBuddy 客户端**：写入认证文件后，**客户端下次启动/登录态重载**才生效。
  切换动作本身包含"关客户端 → 写认证 → 起客户端"，所以点完即可用。
- **CodeBuddy CLI**：只更新**后续加载的会话**使用的默认账号，
  **不会切换正在运行的会话**。要让新账号生效，需要由 ACP 重新加载会话，
  或重启 CodeBuddy CLI。普通 CLI 在同一进程内执行 `/resume`
  **不保证**重新读取认证配置。
- **CodeBuddy CN IDE**：写入后需要客户端重新读取；界面提供"顺带重启"的选项。
- **Trae 系**：切换 = **备份现场 → 关闭客户端 → 恢复目标快照 → 启动**，
  并保留**一代备份**可回退。客户端不关就不能保证快照落地。
- **豆包**：同 Trae，走"启动 → 等待落盘 → 优雅关闭"的保活路径。

**适用版本**：CodeBuddy CLI 的生效语义自 1.0.x 起如此（本页核对于 1.0.46）。

> ⚠ **文档口径**：不要在界面上把"已切换"说成"已生效"。
> CLI 这一条尤其容易被误读成"点了没用"。

### 1.3 区域是账号的一等属性

- 区域由账号库的 `domain` 后缀判定：`.cn` → 国服，`.ai` → 国际版。
- **两个区域的身份命名空间相互独立**：同一串 uid（或同一邮箱）可以同时存在于
  两个区域。账号库的身份匹配因此**带区域**，跨区域**永不互相覆盖**。
- **模型名不通用**：国服与国际版的模型名不同（如国服 `deepseek-v4-flash`、
  国际版 `deepseek-v4.1-flash`）。`GET /v1/models` 返回两区域模型的**并集**，
  但**某个名称能否用取决于实际选中的账号属于哪个区域**；
  不匹配时上游回 `11102`，网关自动换号重试（表现为偶发变慢）。

**适用版本**：1.0.x 全线。

### 1.4 豆包：登录态在**任意** Profile，只抓默认 Profile 必然漏

- 豆包自带账号隔离，登录会话可能位于**任意** Profile。
  只抓 `Default` 会漏掉活跃会话，恢复后客户端打开的活跃 Profile 仍未登录。
  这是**实测根因**，不是理论担忧。
- 恢复前会校验快照的 schema 版本与 leveldb 的 `CURRENT` → `MANIFEST` 完整性，
  并修复 `Local State` 的活跃 Profile 指针。
- **对话正文存在豆包云端**，按账号归属。本地备份的是**客户端状态**
  （会话列表缓存、技能配置）；恢复并重新登录后完整历史会从云端重新同步。
  要把对话带走，用「导出对话」（直接调官方接口拉正文）。

**适用版本**：1.0.x 全线。

### 1.5 Trae：两套 uid 体系，推导失败必须**拒绝入池**

- `storage.json` 里 `iCubeAuthInfo://icube-dc:<uid>` 的 uid 属于
  **账户中心编号体系**；账号库与 JWT `data.id` 属于 **Cloud-IDE 编号体系**。
  同一账号两者**完全不同**。
- 本机发现必须由**使用痕迹**推导 Cloud-IDE uid；**推导失败时明确标记
  「无法确认」并拒绝入池** —— 宁可不给候选，也不产生一个永远登录不上的
  重复账号。

**适用版本**：1.0.x 全线。

### 1.6 抓包凭证回写（豆包）的三条硬约束

1. **目标账号取抓包文件自己的 uid**。用"uid 探测链"定位会因两者来源不同，
   导致两个账号拿到**同一个** sessionid（跨账号污染，实测发生过）。
2. **绝不自动建号**：浏览器网页版与其他字节系应用也会产生豆包 cookie，
   无差别建号会污染账号池。
3. **幂等**：`session_id` / `sid_guard` / `ttwid` 三者都没变时**不写盘**，
   否则每 20 秒的轮询会把文件时间戳刷得毫无意义。

**适用版本**：1.0.x 全线。

### 1.7 「需重新登录」的账号会被**排除出网关账号池**

- refresh token 被服务端**明确拒绝**时，账号被标记「需重新登录」，
  这类凭证**不会**写入网关凭证目录 —— 避免每次请求都白跑一轮再换号。
- 网关页「运行状态」会列出被排除的账号，并指引到「账号管理」页重新登录。
- 重新登录成功后标记被清除，**约 30 秒**的自动同步会把它放回池中。
- **网络失败不等于需要重新登录**：请求根本没发出去（网络不可达 / 代理未启动）
  时只记录瞬时错误，**不打标记**。升级后启动时会自动清理历史误报标记。

**适用版本**：标记机制自 1.0.2x 起；"网络失败不误判"的清理在 1.0.x 后续版本内
（本页核对于 1.0.46）。

## 2. 智能体一键接入与配置生成

- 自动探测 **12 类**客户端（安装目录、配置文件与版本），支持
  Claude Code / Claude Desktop / Codex / DeepSeek Harness / OpenCode / Pi /
  Grok Build / ZCode / Kimi Code / OpenClaw / Hermes Agent / MiniMax Code。
- **多协议适配**：Anthropic Messages（Claude 系）、OpenAI Chat、
  OpenAI Responses（Codex / Grok）。按客户端**实际协议**写入，不写错形状。
- **模型注入**：排第 1 位的自动作为默认主模型；
  Claude 系按 **Sonnet / Opus / Haiku / Fable 四槽位**顺序映射。
- **每次写入前自动备份**，卡片「备份历史」可一键回滚到任意历史版本。
- **批量更新**逐客户端容错执行：**单个失败不影响其他客户端**。
- **接入会覆盖各客户端现有的网关配置**（每次均自动备份）。
  以 Claude Desktop 为例，使用**独立的 3P profile**，
  与其他同类工具的配置互不覆盖。
- **MiniMax Code** 走 Anthropic Messages 协议；接入时注册本网关并指向它，
  **原有的 MiniMax 官方 provider（含 `managed-login` 登录态）原样保留** ——
  官方账号与本网关可同时存在、随时切换。

**适用版本**：1.0.17 起 Trae 进入智能体管理；1.0.x 全线 12 类客户端
（本页核对于 1.0.46）。

## 3. 兼容网关：路由语义

### 3.1 模型名前缀协议：`[产品:][区域:]模型名`

四种写法都支持（README 称"四层路由前缀"）：

| 写法 | 含义 |
|---|---|
| `模型名` | **不限制**产品与区域 |
| `区域:模型名` | 只在该区域选号 |
| `产品:模型名` | 只在该产品选号 |
| `产品:区域:模型名` | 同时限制两者 |

**三条容易改坏的硬约束**：

1. **无前缀时产品/区域是"不限制"，不是默认国服**。
   若默认成国服，**所有国际版账号会静默从候选池里消失**。
2. **未知前段必须原样保留**：`deepseek:v3` 里的 `deepseek` 不是前缀，
   剥掉它就是把模型名本身吃掉（上游回"模型不存在"，而原因在网关）。
3. **最多剥两层，且产品/区域顺序可颠倒**：
   `global:qoder:x` 与 `qoder:global:x` 等价。

**大小写规则**（有意不一致，别统一）：

- **产品**前缀**大小写不敏感**（`Qoder:` / `QODER:` 都接受），
  且**不接受任何别名** —— 产品标识是机器用的，不该有歧义。
- **区域**前缀**大小写敏感**：`Cn:` 不会被当成前缀（区域是短英文词，
  容易与模型名混淆）。

**区域可接受的写法**：`cn` / `国服` / `国内` → 国服；
`global` / `国际版` → 国际版。

> ⚠ 「国服」「国内」**不是锦上添花**：`/v1/models` 下发的组合名用的就是「国服」。
> 不接受它，用户从界面抄下来的写法会被当成裸模型名 ⇒ 上游 `11102`。
> 这是**自相矛盾**（我们给的写法自己读不回来），实测缺陷。

### 3.2 前缀只是"给网关的选号指令"，出站前必须剥离

前缀原样转发会得到
`400 code=11102 model [cn:glm-5.2] service info not found` ——
即"前缀成功约束了选号，却让请求本身失败"。**实测：带前缀的请求全部 11102，
无前缀的同名请求正常。**

### 3.3 `GET /v1/models` 的展示口径

- 下发**裸名**条目，并在其 `aliases` 里附带组合名。
- **组合名同时作为独立条目返回**：很多 OpenAI 客户端只读 `data[].id`，
  只挂 `aliases` 会让用户在模型选择器里**根本看不到**组合名。
- 组合名条目**不再带 `aliases`**（否则会递归展示成一片）。
- 组合名只为**确实有账号的区域**生成 —— 无脑给所有区域会造出
  `qoder:国服:xxx` 这类永远选不出号的条目。
- 列表是**并集**：列表里有 ≠ 抽到的那个号能发。

### 3.4 三协议互转

- `POST /v1/chat/completions`（OpenAI Chat，流式 / 非流式）
- `POST /v1/messages`（Anthropic Messages；Claude Code / Claude Desktop 3P）
- `POST /v1/responses`（OpenAI Responses；兼容 Codex CLI 0.146+）
- `GET /v1/models`

**错误码**：三个入口共享"谁来判定失败类别"的映射链，
**但不是同一个码面值** —— 把码面值也统一会让各协议的词汇表互相串味。
Chat 用专属码，Messages / Responses 用各自的 `invalid_request_error` /
`api_error` / `upstream_error`。详见 §5.3。

**适用版本**：Responses 接口 1.0.x 全线（本页核对于 1.0.46）。

## 4. 选号与容灾

### 4.1 到期分层：让"先烧快过期额度"成为**确定性**行为

两级策略：

| 层级 | 规则 | 目的 |
|---|---|---|
| 1. 到期分层 | 按"最近到期积分"的到期日把候选分组，**只保留最早到期的那一档** | 把概率行为变成确定性行为 |
| 2. 档内挑选 | 同档内按"闲置补偿 + 成功率"加权取 Top5，再加权随机 | 同一天到期的账号**平均分摊** |

关键边界：

- **用"日"而非精确时刻做分层键**：上游额度按天失效，同一天到期视为同一档。
- **档内权重去掉积分项**：同档意味着紧迫度相同；仍按积分加权会让高积分账号
  长期倾斜，与"同档平均分摊"相悖。
- **到期日未知的账号排最后**：只在其它账号都不可用时才轮到它们。
- **全部候选都没有到期信息时退回原三因子口径**（含积分项）。
- **非 WorkBuddy 产品豁免积分分层**：Qoder / ZCode 的额度不是"积分 + 到期日"
  模型。把它们一起分档会让它们**永远排在 WorkBuddy 的到期档之后**
  （没有到期日 ⇒ 被当成最晚）。全是其它产品时退化为随机。
- **档位随消费实时变化**：某账号把快过期额度烧完后，档位跳到下一档并
  立刻让出流量。因此有独立的**积分到期巡检**（默认 **15 分钟**，
  账号间隔 300ms），只刷新余额与到期日，**不签到、不改账号状态**。
- 到期日**持久化**，重启后立刻恢复分层，无需等首轮巡检。

**界面**：账号池显示 `到期 MM-DD` / `到期未知`。

**适用版本**：1.0.x 全线（本页核对于 1.0.46）。

### 4.2 「兜底清单」不能参与「声明」竞争

清单**分两份**，语义严格区分：

| 来源 | 参与「不排除」 | 参与「声明」 |
|---|---|---|
| 宿主透传（上游**真实查询**） | ✅ | ✅ |
| 网关内置静态表（**猜测**） | ✅ | ❌ |

即「不知道某产品提供什么 ⇒ **别排除**它，但也**别声称**它提供」。

> ⚠ **改动前的必问**：加任何"补全清单"的逻辑前，先问**它会被当成声明吗？**
> 若会被当成声明，就必须走 fallback 那条路 —— **猜测永远不该赢过事实**。

**为什么**：兜底清单一旦参与"声明"，账号多的平台会与真正提供该模型的平台
**竞争**并以数量压倒（实测 19:1），选中其实没有该模型的账号。

**例外（权威兜底）**：对 Trae，兜底清单派生自**唯一模型名真相**表，
因此对 Trae 是**确定**而非猜测，可以参与排除判断。

**适用版本**：1.0.32 引入"实测清单只放宽不声明"；1.0.33 引入
"权威兜底"；本页核对于 1.0.46。

### 4.3 熔断与冷却：两类"不可用"必须分开

| 类型 | 触发 | 影响范围 | 恢复方式 |
|---|---|---|---|
| **余额欠费** | 402 / 余额关键词 / 业务码 14018 | **整个账号** | 签到或充值（硬冷却至**次日 04:00**） |
| **模型冷却** | 429 code=6004 | **仅该账号的那个模型** | 到上游给出的重置时间 |

**为什么必须区分**：6004 的上游文案明确写着「您也可以切换其他模型继续使用」——
该账号**其他模型仍然可用**。按账号整体冷却会连带浪费这些额度；
只当普通 429 处理（固定 60 秒软冷却）则 60 秒后继续撞限流，
而真实重置时间常达数小时。

模型冷却的四条边界：

- 冷却**按 账号+模型 记账**，不碰账号级状态；账号池里该账号仍显示"健康"。
- 到期时间**取自报错文案**，支持 `UTC+8` / `UTC-5` / `Z` / 无时区（按本地），
  **且只接受未来时刻**（防重放旧日志写入已失效冷却）。解析不出才回退固定软冷却，
  并在界面上标注。
- **路由三个入口都过滤**：普通选号、粘性命中、全冷却兜底 ——
  少任何一个都会撞回同一个 6004。
- **不喂熔断器**：模型限流是配额信号而非账号故障。
- **持久化**：重置时间常达数小时，而网关会因切换工作模式/重启而重启；
  不持久化则重启即遗忘。

**界面上两者分开表达**（健康账号不显示明细区）：

```text
[模型冷却] deepseek-v4.1-flash          09-15 13:25 恢复（剩 6 小时 40 分钟）
模型冷却只影响上述模型，该账号的其他模型仍可使用。
```

余额欠费则在同一位置显示 `[余额欠费] 余额不足（积分欠费），等签到或充值后恢复`，
**两种情形可同时出现**。

### 4.4 熔断参数与"熔断不是停服"

- 连续失败 **3** 次触发熔断；基础熔断时长 **30 分钟**，
  指数退避**封顶 6 小时**。
- **单账号产品必须兜底**：产品前缀请求的候选集锁死 product，
  严格路径刻意不兜底 ⇒ 该产品只有 1 个账号时，一次上游瞬时故障会被放大成
  **整个产品不可用 30 分钟**（用户看到 `503 no_healthy_account`）。
  因此"该产品一个健康号都没有"时必须退到**同产品内部**的冷却兜底。
- ⚠ **兜底绝不能跨产品**：`qoder:` 是用户的显式指令，把别的产品账号拿给它用
  会拿错凭证、打到错的端点。
- ⚠ **多账号产品的熔断保护不受影响**：只要有一个健康号，严格路径就返回了，
  兜底分支根本不执行。

**适用版本**：1.0.x 全线（本页核对于 1.0.46）。

### 4.5 上游风控熔断（3012）：**立即停止换号**

识别 ZCode 的 `3012 unusual activity` 后**立即停止换号** ——
换号只会让上游看到更多凭证被打，放大风控。窗口内直接快速失败并说明原因。

**边界**：

- 判据是**单个**账号吃到 3012（不需要"多个账号才成立"）——
  它已在官方客户端上复现，与本机账号池**无关**。
- **刻意不罚账号**：3012 与账号无关，罚号会让好账号被冷却。
- **按 (产品, 区域) 隔离**（两层都必要）：
  - **产品**：ZCode 的风控不能阻断 Qoder / WorkBuddy。
  - **区域**：国服与国际版打的是**两个完全不同的上游**（`codebuddy.cn` vs
    `workbuddy.ai`），一侧风控推不出另一侧也在风控。
    ★ 2026-10-16 补上这一层：此前只按产品做键，而**国服与国际版同属 `workbuddy`**
    ⇒ 一个国际版账号吃到 3012 就把国服账号一起熔断 90 秒（现场：「不轮换国内账号，
    直接死掉」）。见 DECISIONS.md D18。
- 熔断期**一个请求都不发**（不区分是否第一轮）。写"第一轮跳过"听起来合理，
  实际却让熔断期间每个新请求仍会打一次上游 —— 用户每重试一次就再撞一次风控。

**★ 账号被上游限制（403 `11140`）不是 3012 —— 两者处置完全相反**：

上游对**被限制的账号**回的 body 里，`displayMsg.en` 含 `unusual activity`
（「Your account has been restricted due to unusual activity」），
而 3012 的判据之一是**全文子串**匹配该短语。

★ 2026-10-16 修：此前它被**误判成 3012** ⇒ 坏号不被冷却（3012 刻意不罚账号）
**且整个 (产品, 区域) 被熔断 90 秒** ⇒ 同区好号一起被挡。
现场形状：12 个国际版账号里 **11 个好 + 1 个被封**，却「发送就直接死」。见 D20。

| | 11140 账号被封 | 3012 请求级风控 |
|---|---|---|
| 归属 | **账号侧** | 请求 / 出口侧 |
| 处置 | 软冷却该号 + 换号 | 熔断区域 + 不罚账号 |
| 换号有用吗 | **有用**（换号即好） | 无用（换号加重风控） |

⚠ 被封账号**自己仍然不可用**：上游给了 `SUBMIT_FEEDBACK` 申诉入口，
只能去官方客户端申诉。**补 device token 也救不回来**（见 D19 / §4.7.2）。
本修复的作用是让它**不再拖累同区其它账号**。

**同类但不同的另一条 —— 出口 IP 被 WAF 拦**：
判据是**多个不同账号**在短时间内一起被拒（同一账号反复被拒才是账号问题）。
出路是查本机网络出口（代理 / VPN / 公网 IP），**换号无用**。

**三条判据的区分要点**（都碰 403/405，别混）：

| 现象 | 判据 | 换号有用吗 |
|---|---|---|
| 3012 风控 | body 业务码 `3012` 或含 `unusual activity`，且**不是** 11140 | ❌ 无用 |
| 11140 账号被封 | body 业务码 `11140` | ✅ **有用** |
| WAF 出口 IP 被拦 | **≥2 个不同账号**短时间内一起 403 | ❌ 无用 |

**适用版本**：3012 熔断 / 11140 账号侧冷却 / WAF 判定 1.0.x 全线
（本页核对于 1.0.46；11140 与 3012 的区分修复见 D20）。

### 4.6 空流风暴：上游整体故障时不再"全量换号"

上游整体吐不出内容时，**不再把每一个号都试一遍再全部记一笔** ——
那种"全量换号"会把一次上游故障放大成账号池级故障
（熔断 + 兜底捞号 + 再耗尽，正好撞上客户端并发重试）。

- **多号同通道空流** ⇒ 判定为上游整体故障，中止本轮轮转，
  **不罚任何账号**（按 产品+区域 记账，窗口 60 秒）。
- **单号空流** ⇒ **不罚号**，仅换号；风暴窗口已记账，靠"不罚 + 正常轮转"自愈。
- 空流**不再等同于额度耗尽**：旧实现硬编码"额度耗尽"，
  只要某账号回一次空流就被整号硬冷却到次日 04:00 ——
  而空流的原因很多（上游抖动 / 网关闪断 / 代理超时），与额度毫无关系。
- 轮转耗尽时报**专属契约**并如实描述，**不报** `no_healthy_account` ——
  后者会诱导客户端立即并发重试（现场正是 5 路重试把账号全拖进冷却）。

**适用版本**：1.0.40（风暴窗口）+ 1.0.41（空流不罚号、如实报因），
2026-10-11；本页核对于 1.0.46。

### 4.7 并发上限与"客户端并发重试"的相互作用

- `pool.max_in_flight` = **单账号**在途请求上限，默认 **3**（0 = 不限）。
- ⚠ **任何"每账号"的上限，在单账号产品上就变成了"每产品"上限** ——
  设计时必须问「这个产品只有一个号时会怎样」。
- **客户端的重试次数是并发度的信号**：DSH 用的 `@earendil-works/pi-ai`
  带 `retryProviderRequest`，默认**重试 5 次**，
  而**每个重试是独立的并发请求**。曾只有 3 ⇒ 5 次重试里后 2 次必然 503。
- **定位方法**（值得记住）：用**并发梯度**找边界 ——
  实测"并发 3 全通、并发 4 起失败"，直接把 `max_in_flight=3` 钉死为根因。
- 另有**单请求最多换号次数** `pool.max_rotate`，默认 **3**；
  重试与换号**共用同一个循环**，因此循环上界是两者之和
  （否则重试会把换号预算吃光）。

> ⚠ **一处待 Owner 定口径的分叉**：本仓库 AGENTS.md / README 提到
> `InFlightWait`（默认 3000ms）"在名额满时**排队**而非失败"。
> 该描述属于 **Go 对照实现**（`go-gateway/`）；
> **当前 Rust 网关未发现对应的等待逻辑** —— 占名额失败时直接换号重试。
> **不要把 Go 侧的行为当成产品承诺**；本条已列入 §10 留白。

**适用版本**：`max_in_flight=3` / `max_rotate=3` 自 2026-09-22 起；
本页核对于 1.0.46。

### 4.7.1 上游请求身份：按区域分流 + 会话头族（2026-10-16 补回）

网关冒充官方客户端与上游对话，**请求身份**（UA + 身份头 + 会话头）决定上游认不认我们。
这两块在 Rust 重写时**整体丢失**，2026-10-16 按 Go 参照实现补回。

**① User-Agent 必须按区域分流**：

| 区域 | UA |
|---|---|
| 国服 | `CLI/2.63.2 CodeBuddy/2.63.2` |
| 国际版 | `WorkBuddy/5.6.2 WorkBuddy/5.6.2 CLI/2.147.0` |

实测（同一账号 / 模型 / 端点）：国际版发国服 UA ⇒ `403 {"code":11140,"msg":"request illegal"}`。
⚠ 这个 403 在客户端界面上还会被渲染成「API 密钥无效」，**排查方向会被彻底带偏** ——
「UA 错了不报错，只会 403」。

**② 国际版专属身份头**（**只在国际版发**）：`X-IDE-Type` / `X-IDE-Name` /
`X-IDE-Version: 5.6.2`、`X-Agent-Intent: craft` / `X-Agent-Purpose: conversation` /
`X-Agent-Type: main`、`x-codebuddy-request: 1`。

**③ 会话头族**（**三套身份、两个区域都发**）：
`X-Conversation-ID` / `X-Conversation-Request-ID` / `X-Conversation-Message-ID` /
`X-Request-ID`（后两者同值）。缺了它上游**渠道校验**回
`400 / code 11-128` `conversation id missing`（「这次调用没通过渠道校验，
可能不是官方客户端发出的」）。

- `X-Conversation-ID` 由**会话键确定性派生**（`uuid5(NAMESPACE_URL, seed)`，大写）。
  官方客户端**整段会话复用同一个** id；每次新造会让上游看成「一串互不相干的单轮请求」。
- 会话键取请求体的 `metadata.conversation_id`，**换号重试时保持不变**。

⚠ **国服不发国际版专属身份头**：国服上游不认它们，多发等于改变国服的请求画像，
而国服是主力通道。有测试专门钉住这条（防「修过头」）。
会话头族则相反 —— **不分区域**，因为参考实现里三套身份都带。

### 4.7.2 国际版的 `X-Device-Token`：拿不到会**逐步被风控标记**（2026-10-16 修复）

官方客户端**每个请求**都带 `X-Device-Token`（`v3:` 形态，约 1030 字符），
由腾讯 TuringShield SDK 生成。网关经宿主服务 + Node 子进程复用该 SDK。

**它只对国际版发**（国服没有抓包证据，不该外推）。

## 关键：拿不到 ≠ 请求失败，而是**长期被标记**

取不到 token 时网关**静默降级**（不发该头、请求照常）—— 这是刻意的，
避免把「可选增强」变成「新的单点故障」。**但代价是**：

> 长期缺设备凭证会被上游**风控逐步标记**。

所有者的现场就是这条：12 个国际版账号因 SDK 目录发现失败**全部拿不到** token，
随后出现 3012 `unusual activity`（日志里 3012 与取 token 失败**1:1 对应**）。

## SDK 目录发现（2026-10-16 起）

- 扫描**所有已知客户端**：`WorkBuddyAI`（国服）/ `WorkBuddyAIGloable`（国际版）
  / `CodeBuddy CN` / `CodeBuddy` / `WorkBuddy`，任一个可用即采用。
  ★ 客户端目录名与账号区域**并非一一对应**，机器上可能只装其中一个。
- 判据是「**原生模块存在**」（`build/Release/turing_sdk.node`），
  **不要求**客户端自带 `index.cjs` —— 那只是 1.2 KB 的 require 垫片，
  国服客户端目录里就没有；垫片由**我们自带**（`turing-sdk-shim.cjs`）。
- 原生文件（`turing_sdk.node` + `TuringShieldSDK.dll`，共 1.6 MB）是**腾讯闭源二进制**，
  仍必须来自已安装的客户端 —— 我们只摆脱了对那个 JS 垫片的依赖。

## ⚠ 已被标记的账号补 token 也救不回来

实测（2026-09-28，9 个国际版账号三组对照）：`403 11140` 的账号带上任何
device token **仍然 403** —— 那是服务端的 (设备,账号) 绑定状态，
**只有重新登录才能恢复**。本项修复的作用是**阻止新的标记产生**。
**适用版本**：2026-10-16 起（见 DECISIONS.md D18）。

### 4.8 会话粘性与成本守卫

- 同一会话**尽量绑定同一账号**，绑定 TTL **30 分钟**，滚动续期，
  失败自动解绑。
- **粘性快路径必须尊重成本维度**：会话一旦绑到计费号，30 分钟 TTL 内
  所有请求都走它 —— 成本维度形同不存在。
  实测形状：15 个计费账号被**均匀**摊了 710 条（45–50 条/号，极均匀 ⇒
  会话各自绑到不同号），每条平均 27 万 input token。
- 绑定号"确定计费"而池里存在"确定免费"的可服务候选时，
  **解绑并走完整选号**（那里成本维度生效）。

**适用版本**：成本守卫自 1.0.36（2026-10-08）；本页核对于 1.0.46。

### 4.9 平台总开关：粒度与"任务照跑"

- 关掉某个平台的"参加兼容网关路由"后，它的账号**不参与选号**；
  **签到 / 上报 / 成长任务 / 额度巡检照常运行**。
- 这条判据**必须在选号之前**：实测它最初只写在"选不出号"分支里，
  而带产品前缀的请求走另一条路径 ⇒ **关掉 qoder 后
  `qoder:国服:GLM-5.3` 依然返回 200**（真上游内容），开关形同虚设。

  —— 因为**出路完全不同**（一个去账号页打开开关，其余去查账号）。

**适用版本**：1.0.x 全线（本页核对于 1.0.46）。

## 5. 报错文案与失败原因

### 5.1 ★★ 客户端判「API 密钥无效 / AUTH」是按**文案正则**，不是状态码

**这是本页最重要的一条规格。**

**现场（2026-09-20，所有者报告）**：

> 「密钥明明是正确的，不知道怎么对话过程中就提示『本轮运行失败 API 密钥无效』，
> 而且我还是可以通过我配置的密钥获取到模型的名称」

**查证结论：密钥从头到尾都是对的，是错误信息被客户端误读了。**

**真正的判据（2026-09-29 更正）**：客户端按**文案文本正则**判 AUTH：

```text
if (/\b(?:401|403)\b/.test(message)) return "AUTH";
```

而错误文案来自上游响应体，适配层会把 `(status): body` **原样拼进 message**。

> ⇒ **只要文案里出现裸 `401`/`403`，不管 HTTP 状态码是什么，都被判 AUTH。**

**这就是为什么"只把 403 改写成 502"是无效的** —— 上一版正是这么做的，
所有者装了新包实测**仍然**报「API 密钥无效」，
因为文案里还留着「上游 403 业务码 11140」这几个字。
**光改状态码治不了这个病。**

**因此有【两道】防线，缺一不可**：

| 防线 | 规则 |
|---|---|
| 状态码 | 上游 403 → **502**；其余原样 |
| 文案 | 在**所有**对外出口把**裸 401/403** 就地改写成 `4xx` |

**硬约束（改任何面向客户端的文案前必读）**：

1. **面向客户端的文案绝不能含独立 `401`/`403`**。
2. **业务码必须原样保留**：`11140` / `14018` / `11133` / `11102` /
   `11115` / `4028` / `10605` / `6004` / `3007` 逐字不变。
3. **`14018` 是最危险的一个**：它的中间三位**正好是 `401`**。
   靠**词边界**保护（`14018` 里 `401` 左侧是 `1`，是单词字符 ⇒ 无边界 ⇒ 不动它）。
   若实现里用了裸的"包含 401 就替换"，它会变成 `14xx8`，
   把上游的业务码改坏，**用户再也查不到真实错误**。
4. **`4028` 是同一类陷阱**：它**内含** `402` 子串，右侧是数字 ⇒ 不得被改写。
5. **`429` / `400` / `413` / `5xx` 原样保留** —— 这些数字**不是** AUTH 判据
   （正则只认 401/403），改掉它们只会让用户失去"该不该重试"的信息。
6. **改写必须是幂等的**：网关有多层出口，同一段文案可能被过两次。
7. **我们自己的 401 保持 401**：那是我们自己的鉴权结果，**必须**保持，
   让客户端提示"密钥无效" —— 那种情况下提示是**对的**。
   我们自己的 401 文案是 `missing or invalid API key`（不含裸数字），
   改写是恒等变换。
8. **我们自己从不回 403**（鉴权中间件只用 401），
   所以把上游 403 改掉不会与"我们自己的拒绝"混淆。

**「裸」的定义**：前后都不是**单词字符**（`[0-9A-Za-z_]`）。
⚠ 这里的单词字符**只认 ASCII**：

```text
"上游403业务码"
  按 ASCII 词边界  ：游 / 业 都不是 ASCII 单词字符 ⇒ 有边界 ⇒ 命中 ⇒ 改成 "上游4xx业务码"
  按 Unicode 词边界：游 / 业 都是 Unicode 单词字符 ⇒ 无边界 ⇒ 漏判（裸 403 留在文案里）
```

而**"紧贴中文的裸 403"正是真实上游文案的常见形状**。
漏判的后果就是本缺陷原样复发 —— 用户又看到「API 密钥无效」。

**两个方向的收益不对称**：漏判让修复失效；误判只是多改写一个数字串
（`4xx` 同样不含裸 401/403，客户端仍走可重试分支，不会更糟）。
⇒ 判不准时**宁可按边界处理**。

**出现裸 401/403 时网关会打一行告警日志**：说明**某处文案自己带上了状态码**，
应当去修那个产出点，而不是长期依赖这道闸门兜着。

**适用版本**：判据更正于 2026-09-29；本页核对于 1.0.46。

### 5.2 为什么 403 → 502（而不是保留 403）

语义上 403 是"服务器理解请求但拒绝执行"，属于**上游**的决定；
而 401 才是"你没带对凭据"。403 被客户端当成凭据问题纯属误读。
**502 Bad Gateway** 准确表达"上游拒绝了 / 不可用"，
且客户端不会把它归类成 AUTH，而是走 **可重试** 分支 —— 那才是正确的语义。

### 5.3 错误码契约（Chat 入口）

| 场景 | HTTP | Chat 错误码 | 出路 |
|---|---|---|---|
| 上下文超出模型窗口 | 400 | `context_length_exceeded` | 压缩/清空会话、调小最大输出 |
| 请求被上游拒绝（11155 思维链缺失） | 上游原值 | `invalid_request_error` | 改请求 |
| 模型不在**用户白名单** | 400 | `model_not_allowed` | 去「兼容网关」页放行 |
| 模型不在**上游清单** | 400 | `model_not_in_upstream` | **换模型**（放行也没用） |
| 模型不在**这条通道**（11102） | 400 | `model_not_in_region` | 换模型或加区域前缀 |
| 请求参数被模型提供商拒（11133） | 400 | `model_param_invalid` | 缩小上下文 / 调小输出 / 换大窗口模型 |
| 思考档位被拒 | 400 | `reasoning_effort_rejected` | 换档位 |
| 平台总开关关闭 | 400 | `platform_not_in_routing` | 回账号页打开平台开关 |
| 白名单不放行"平台 × 区域 × 模型" | 400 | `model_not_in_product` | 去白名单加模型 |
| 该账号在这条通道没有资源包（1113） | 400 | `no_resource_pack` | 换账号或换套餐内模型 |
| 账号额度耗尽（402） | 402 | `quota_exhausted` | 充值 / 等签到 |
| 上游要求人机验证（3007） | 503 | `captcha_required` | 去官方客户端过验证 |
| 上游风控（3012） | 503 | `unusual_activity` | **不要立即重试** |
| 出口 IP 被 WAF 拦 | 503 | `egress_ip_blocked` | 查代理 / VPN / 公网 IP |
| 上游整体空流 | 503 | `upstream_stream_stalled` | 稍等片刻 |
| 其余上游失败 / 账号全不可用 | 503 | `no_healthy_account` | 等冷却恢复 |
| 账号全被设为不参与选号 | 503 | `no_healthy_account` | 去打开路由开关（**不是故障**） |
| 本机每日护栏 | **429** | `rate_limit_exceeded` | 等本地零点 / 调旋钮 |

**Messages / Responses 入口**：除 `context_length_exceeded`（Responses 同名）外，
上述请求侧错误统一落各自的 `invalid_request_error`；
可用性问题落 `api_error` / `upstream_error`。

**为什么必须分成这么多码**：每一条的**出路完全不同** ——
换档位 / 换模型 / 加区域前缀 / 改参数 / 打开开关 / 改白名单 / 充值。
合并成一个 `invalid_request_error` 会让客户端只能一律提示"请求有问题"，
用户不知道该改哪一项。

**三条最容易合并错的**：

- `model_not_allowed`（白名单）**≠** `model_not_in_upstream`（上游没有）——
  **出路恰好相反**：前者"去白名单里放行"，后者"放行了也没用"。
  混用会让用户**反复去配置页加一个不存在的模型**。
- `model_not_in_product` **≠** `platform_not_in_routing` ——
  一个去改白名单，一个回账号页打开平台开关。合并会让用户改一个
  与故障毫无关系的配置，改到天亮也不会好。
- `quota_exhausted`（真的没钱）**≠** `no_resource_pack`（只是这个模型
  不在该账号的套餐里，额度可能一分没花）—— 前者要充值，后者只要换号。
  用错会让用户拿着一个额度满格的账号去充值。

**请求体超限**：上限 **32MB**（`32 << 20`），超限返回 **413** 并说明原因，
三个协议入口行为一致。超限与"读取失败"用**不同的码**（客户端按自家词汇表分支处理，
混用会让错误提示退化成未知错误）：

| 协议 | 超限 | 读取失败 |
|---|---|---|
| OpenAI（chat/completions、responses） | `payload_too_large` | `invalid_request` |
| Anthropic Messages | `request_too_large` | `invalid_request_error` |

> 为什么提到 32MB：旧上限 8MB 用 `LimitReader` 读满即返回，
> 调用方**无法区分"读完了"与"被截断了"**；截断后的字节不是合法 JSON，
> 原样透传给上游，上游报 `11101 unexpected EOF` ——
> 客户端只看到"请求参数有误"，**无法定位到是网关截断**。

**适用版本**：错误码契约与 32MB/413 自 1.0.x（本页核对于 1.0.46）。

### 5.4 几条文案的措辞是**硬约束**，别顺手改

**① 11133 必须"说人话"，不许说"拒绝"**（2026-10-09 所有者原话：
「把 11133 workbuddy 这个报错更明显，**就说人话**，不要再说拒绝了」）

- 旧文案「上游**拒绝**本次请求的参数…请检查请求参数后重试」有三层问题：
  **甩锅给用户**（实测最常撞上它的原因是上下文/输出预算超了，
  不是"参数写错"）、**信息量为零**（上游的 `param` 实测**恒为空串**）、
  **真因被埋掉**。
- 新文案的**必备要素**：第一句就说"这次请求**太大了**"；
  明说"**这不是账号问题，换账号无效**"；给三条可操作出路
  （缩小上下文 / 调小输出 / 换上下文更大的模型）。
- **必须保留** `code=11133` 与上游原文：前者是与用户对账的唯一线索，
  后者用户拿去搜能对上官方文档。上游原文要**标注为"上游原话"**，
  与我们的解释区分开 —— 它把预算超限说成"参数被拒"，
  正是本节要纠正的那个误导性口径。
- ⚠ **刻意不出现「拒绝 / 退回 / 参数错误」这些词**。

**② 11102 必须与"排队"区分清楚**（10605 是排队，稍后可用；11102 等多久都没用）

文案里必须写明"**不是排队，等多久都不会出现**"，并给出两条出路：
换模型，或用「平台:区域:模型名」的写法明确指定区域。

**③ 11140 的文案不能出现 "403"，也不能透出上游原文**

- 归因改用**业务码 11140**（对排查同样唯一，且不含任何会被误判的数字）。
- **不透出上游原文**（`request illegal` 那种措辞会让人以为是自己请求写错了，
  而**实际请求完全合法**）。
- 措辞必须说清"账号在本设备尚未完成登录"，并指引去「账号管理」页重新登录。

**④ 空流 / WAF / 3012 三类文案的三条共同硬性要求**

1. **必须说清"账号是好的"** —— 否则用户看到失败会去逐个检查账号；
2. **不能出现裸 401 / 403**；空流那条**也不写裸 503**
   —— 同样可能被客户端按状态码语义解读成"服务过载，请重试"；
3. **不能诱导立即重试**（现场客户端是 5 路并发重试）：
   出路写成"稍等片刻"，并给出窗口自动解除的时长，
   让重试天然错开上游故障期。

**⑤ 每日护栏的文案必须按成因分叉**（见 §7）。

**⑥ 3012 文案刻意不说"账号被封"**

实测同一账号一分钟后就成功，且官方客户端也吃它。
说成封号会把用户引向"去换账号"这个**完全无效**的方向。

**适用版本**：① 自 1.0.38（2026-10-09）；②③④⑥ 自 1.0.x；本页核对于 1.0.46。

### 5.6 思考档位的两条行为约定

## 6. 流式收尾语义

### 6.1 ★★ 上游"先宣告 finish_reason、后写 [DONE]"时**不得判失败**

**现场（2026-10-07，所有者原话）**：

> 「对话过程中对话会输出完就中断，这是我为什么回退版本的原因」

**根因**：上游收尾顺序 = **先**给 `finish_reason`、**后**写 `[DONE]`，
两者之间那一瞬最容易被掐断（`usage` 也还没落下来）。
旧判据只看"有没有 `[DONE]`" ⇒ **内容已完整却判成本轮失败**
（补 error 帧 → 客户端显示"本轮运行失败"）。

**实测形状**：16 条 `saw_done=false`（**全为国际版账号**，
已收 29,628–1,992,314 字节）+ 18 次
`upstream stream truncated`；失败率 **16/13,780 ≈ 0.12%**；
断流集中在**请求发出后 32 ms – 6 s**、多会话几十到几百毫秒内**齐断**
⇒ 共享通道抖动（与账号/模型无关）。

**修法（这是规格，不是实现细节）**：记住"已经给过**非空** `finish_reason`"，
读错误分支在**已宣告完成**时只补一帧纯 `[DONE]` **正常收尾**，不补 error 帧。

**为什么值得放宽**：回答已经写完，用户却看到"本轮运行失败"，
客户端随后**整轮重试 —— 重新生成一遍**，
比丢掉一个终止字节昂贵得多。

### 6.2 ★ 真截断**仍必须报错**，语义没有被放宽

以下情形**仍然报错**，并**换账号重试**：

- **首帧之前就断** ⇒ 503 + **换账号重试**。
- **吐了一半就断**（`finish_reason` 没到）⇒ 报错，语义不变。

**判据（四情形，可直接当验收标准）**：

| 情形 | 判定 |
|---|---|
| 见过 `[DONE]` | 正常收尾 |
| 没见过 `[DONE]`，且**一个 data 帧都没读到**（空流） | 正常收尾（合法的空回合，无损） |
| 没见过 `[DONE]`，但**已经吐过内容** | **失败**（补 error 帧） |
| 见过**非空** `finish_reason`、只差 `[DONE]` | 正常收尾（只补 `[DONE]`） |
| 见过**失败语义**的 `finish_reason` | **失败**（补 error 帧） |

**为什么"吐过内容但没 `[DONE]`"必须判失败**：补一帧
`stop_reason=end_turn` 等于告诉客户端"模型答完了"，
它会据此推进对话，**用户只看到回答被从中间截断**。

**为什么只有【非空】`finish_reason` 才算"给过"**：
上游偶尔发 `"finish_reason":""` 的空帧，把它当结束信号会让客户端**一直等**。

### 6.3 失败语义的 `finish_reason`：上游用**正常帧的形状**宣告失败

**现场（2026-10-12，所有者原话）**：
「为什么这个模型在对话过程中一直在中断?你看看咋回事」

**根因**：上游对单轮生成有约 **900 秒**的硬上限（实测跨度
900.572s / 900.701s / 892.7s），超时后**不回 HTTP 错误**，
而是在流尾写一帧 `{"choices":[{"index":0,"delta":{},"finish_reason":"error"}]}`
就收尾。这类帧**不带 `error` 字段、形状完全合法**，
旧口径下网关侧连一条日志都没有，客户端把它翻成
**不可重试**的 `Provider finish_reason: error`。

**规格**：

- **只认实测过的取值 `error`**：`stop` / `length` / `tool_calls` 都是**正常收尾**，
  把它们算成失败会让**每一次正常回答都被补一帧 error**。
- **失败语义的取值【不算】"已宣告完成"**：它恰恰是"这一轮没答出来"。
  若把它算成完成，截断就永远不会被报出来，
  用户看到的就是"对话一直在中断"却查不到原因。
- 两种形态都要认：迭代器内部拿到的是**裸 JSON 载荷**，
  而收尾逻辑拿到的是带 `data: ` 前缀、带结尾空行的**整帧文本**。
  **只认一种会让判定在真实链路上永远不生效**（第一版踩过这个坑）。

**适用版本**：1.0.43（2026-10-12）。

### 6.4 帧序是硬契约：error 帧必须在 `[DONE]` **之前**

- `[DONE]` 是"流正常收尾"的**权威标志**，不能用 `finish_reason` 代替。
- **同一条流里 `[DONE]` 恰好一个**。
- 截断时必须在 `[DONE]` **之前**插一帧终止性 error，**且该 error 帧自带 `[DONE]`**
  ⇒ 补了它就**不能再把原 `[DONE]` 透传出去**（否则响应体里出现两个 `[DONE]`，
  客户端读到第一个就把这轮标成正常完成，后面的 error 被丢掉）。

> ⚠ **别为了"读起来顺"把帧序调回来**：实测 error 帧排在后面时，
> 响应体尾部是 `…\n\ndata: [DONE]\n\ndata: [DONE]\n\n`，
> **终端错误码根本没有到达客户端** —— 用户看到半截回答，
> 网关侧用量还记成**成功**，等于修复完全没生效。

**为什么是 error 帧而不是补一帧 `finish_reason`**：
补 `finish_reason` 等于替上游宣告"模型答完了"，客户端会把**被截断**的
半截回答当成一次正常完成收下；error 帧则被客户端 SDK 直接抛成 `APIError`，
客户端拿到明确原因并**按可重试错误处理**。

### 6.5 收尾文案的措辞也是契约

截断收尾的文案必须含 `stream ended before` / `stream ended without` 这一形状 ——
客户端用它把这类失败归为 **`TRANSPORT`**，而 `TRANSPORT` 在**可重试**名单里
⇒ 会自动换账号重试（实测重试能拿到完整回答）。
**换个说法就会被归成不可重试**，用户只能对着一个残缺的回答发呆。

⚠ 该文案同样必须过 §5.1 的文案闸门（它会进客户端的错误分类正则链）。

### 6.6 流式请求的**首帧预读**：写响应头之前必须先确认这条流有内容

- 上游有一种失败形态是 **HTTP 200 + 空流**（ZCode 对受限账号返回 200，
  流里一帧有效数据都没有）。若直接放行，后果有两个：
  ① 状态码 200 已经写出去了，**上层再也无法换账号重试**；
  ② 坏账号被记成"成功"、**永不冷却** ⇒ 每次请求都选中它 ⇒
  用户的对话**持续失败**。
- 因此：**首帧之前**判定空流 / 首帧即错误，归为失败并**换账号重试**。
- 超时与"读到帧但帧无效"归**同一句**文案 —— 对用户而言都是"上游没给出内容"，
  区分它们只会泄露内部细节。
- **预读消费掉的字节必须原样交回下游**，否则回答会**少开头几个字**。

**适用版本**：本页核对于 1.0.46。

### 6.7 三种上游收尾形态的**实测期望值**（可直接当验收标准）

| 上游收尾形态 | 客户端应看到 |
|---|---|
| 正常（有 `[DONE]`） | 不补任何东西；`[DONE]` 恒 1 个 |
| 只给 `finish_reason`、不给 `[DONE]` | **只补 `[DONE]`，不报错** |
| 真截断（吐了一半） | **补 error 帧 + `[DONE]`**，且 error 帧在 `[DONE]` **之前** |

**适用版本**：1.0.35（2026-10-08）实测三形态；1.0.34 起放宽。

### 6.8 流式日志（排查契约）

网关在**每条流结束时**都会留一行收尾日志，记录
"已收 N 个有效帧 / M 字节，`saw_done=…`，`saw_finish_reason=…`"。

**为什么这是规格**：此前**流正常结束时一行日志都没有**，
"网关有没有把这条流收干净"**无法回答** —— 只能靠有没有 error 帧反推。
现在：客户端若仍报"流没结束"，而日志里**没有**对应记录，
就能立刻判定断在**网关之外**（客户端插件、本机代理、或客户端自己取消），
不必再对着网关源码猜。

**适用版本**：1.0.35（2026-10-08）起，网关日志**每行都带时间戳**。

### 6.9 流式**心跳**：上游思考阶段长时间零字节时不能让连接被判死

- 上游思考阶段会**长时间零字节**（实测推理模型可达 **20 秒以上**），
  而客户端自带空闲超时、各类反代/负载均衡通常 **60~120 秒**。
- 因此网关周期性发一个**真事件**心跳（间隔 **10 秒**）同时压住这两类超时。
- ⚠ **不能用 SSE 注释帧**（`: ping`）当心跳：客户端解析器会把注释行**直接丢弃**，
  `stream.next()` 根本不返回 ⇒ 定时器**不会被重置**，心跳等于没发。
  **心跳必须是被解析的真事件。**

**适用版本**：本页核对于 1.0.46。

## 7. 账号级每日用量护栏

**适用版本**：**1.0.45** 引入（2026-10-14）；**1.0.46** 修掉两处行为错误。
默认**关闭**，升级后行为与 1.0.44 **完全一致**。

### 7.1 两个旋钮与默认值

| 旋钮 | 默认 | 含义 |
|---|---|---|
| `daily_token_cap` | **0 = 关闭** | 该账号**本地当天**累计 Token 达到上限 ⇒ 今天不再参与选号 |
| `credit_floor` | **0 = 关闭** | 已知剩余积分 **≤** 下限 ⇒ 今天不再参与选号 |

- 两个旋钮都写在配置的**顶层**。
- ⚠ **放进 `pool` 块里会被静默忽略** —— 症状是"旋钮明明写了却毫无效果"，
  而且**一条报错都没有**。改配置时务必确认在顶层。
- 改完**不需要重启网关**：走已有的热重载通道，**当场下发到账号条目**，
  实测约 **4–6 秒**生效，网关进程号不变。

### 7.2 边界：它是**选号闸**，不是限流器，更不是 kill switch

- **只挡新对话，不打断进行中的请求**。用量在**请求结束后**才记账，
  所以"刚用完"到"被挡住"之间有**最多 5 秒**的窗口。
- **不落任何状态**：不写"已禁用"、不写"不参与选号"、不设冷却截止。
  账号照旧被列出、照旧能跑养号任务（**实测被闸住时
  `/tasks/run?task=activity` 仍返回成功**）。
- 它补的是账号退场的**第三档**：此前只有"上游报错（熔断）"与"人工禁用"
  两条路，缺"上游没报错、账号也健康，只是今天不想再烧额度"这一档。
- **账号是好的，护栏是本机设的** —— 文案里不能写成"故障"或"账号不可用"。

### 7.3 ★ 两种成因必须**分开说**（1.0.46 修的就是这条）

| 成因 | 触发 | 恢复方式 |
|---|---|---|
| **额度撞顶** | 当天 Token 达到 `daily_token_cap` | **本地零点自动归零**，用户什么都不用做 |
| **余额跌破下限** | 已知剩余积分 ≤ `credit_floor` | **不随日期恢复**，只能等积分巡撤回充，或把下限调低 |

**1.0.45 的缺陷**：429 文案对**所有**成因都写"过了本地零点自动恢复"。
可**余额跌破下限**这一类**不随日期恢复** ——
用户照着文案**等一个永远不会到来的零点**，
同时**跳过唯一有效的两个动作**（等回充 / 调低下限）。

**1.0.46 的规格**：

- 按成因**分叉文案**；**额度优先于积分**（两个旋钮同时命中时报"今天用满了"
  更贴近用户刚做的事，且那条出路代价更小）。
- 前半句也**不能**写死"用满了每日额度上限"：成因可能是积分闸，
  那时用户**根本没碰过 Token 上限**，写死会把他引到**错的旋钮**上。
- "有账号可用、却一个都选不出来"是**另一类成因**（模型/区域/冷却组合），
  不能套用"全池"的措辞。

**两类文案的必备要素**：

- **全池被挡**：说清"该产品下的可用账号（共 N 个）今天都被你设置的每日护栏
  挡住了"；**"这不是故障"**；给出成因对应的出路。
- **部分被挡**：说清"N / M 个账号撞到了你设置的每日护栏"。
- **积分成因**必须点明"余额**不会**随日期自动回来"。

### 7.4 ★ 计数口径：`total = input + output + cache_write`（**不含** `cache_read`）

- `input` **已经包含**缓存命中部分（与上游 `prompt_tokens` 含 cached tokens 一致）。
- **`cache_read` 不计入总量**：缓存命中**不是真实消耗**，
  算进去会让**长会话提前触顶**。
- **这是唯一的总量口径**：统计页与护栏判据走**同一个**函数。
  若两处各算一套，用户会看到"界面没到上限"而网关已经 429 ——
  那是**最难排查**的一类不一致。
- 账按"账号 × 日期"存，**跨零点不需要定时任务**。
- **昨天的用量不算今天的**（实测：把同样的用量记到昨天再重启 ⇒ 约 3 秒内恢复）。

### 7.5 ★ 积分闸的两个"刻意为之"

1. **"未知不拦"**：积分下限**只对上游成功查到过的余额生效**。
   查询失败时**旧值原样留着**，一个没人成功问过的数字**永远 arming 不了**这道闸。
   这是刻意的 **fail-open**：宁可少拦，也不能凭一个陈旧的持久化数字把账号永久锁死。
2. **"是否知道余额"不持久化**：重启后到该产品第一次巡检之间（最长 15 分钟），
   积分闸**失效**。

> ⚠ **已知边界：`credit_floor` 对 ZCode 号【恒不生效】** ——
> ZCode 没有积分查询接口。这正是"未知不当 0"的原因：
> 把"查不到"当成 0 会把 **ZCode 号全部闸掉**。
> **此边界自 1.0.45 起至 1.0.46 未变，属如实记录的未覆盖面。**

### 7.6 另一条已修的行为错误：Trae 无限额不能"追认"旧余额（1.0.46）

**症状**：明明写着无限额，号却**一直不被选中**。

**根因**：无限额刷新会把快照里**早就过期、根本没重新问上游**的积分值
透传下去，并把"余额已知"置真。一旦那个旧的假值恰好低于下限，
账号就会被**一个没人问过的数字**闸住。

**规格**：只更新到期日的那条分支**不得触碰**积分值与"余额已知"标志 ——
陈旧值必须**从作用域上消失**（想复现这个 bug 必须先把字段加回来）。

### 7.7 真机验收读数（1.0.46）

| 场景 | 期望 |
|---|---|
| 旋钮未开（默认） | 已超量的账号**照常路由**，护栏标记为假 ⇒ **opt-in** |
| 开启上限 | 约 6 秒内全被闸住；chat = **429**；**进程号不变** |
| 被闸住时 | 账号"健康数=0"但"冷却=0 / 禁用=0 / 不参与选号=0"；养号任务仍成功；`/v1/models` 仍 200 |
| 被拦请求 | **不逐条写日志**（3 次被拦给日志加 0 行） |
| 调高上限 | 约 4 秒后解除，**进程全程没重启** |
| 当天用量 + 重启 | 仍 429（启动读盘就武装了护栏） |
| 昨天的用量 + 重启 | 约 3 秒内恢复 |

**适用版本**：1.0.46（2026-10-14）。

## 8. 统计与请求日志

### 8.1 数据来源与计数边界

- 每次**成功**请求结束后，从上游响应（非流式 `usage` 对象 /
  流式 SSE 末帧 `usage`）提取计量，按**服务器本地日期**聚合。
- **上游未返回可用 `usage` 时不计数，也不产生空记录**。
- 全部**按天**存储，导出时可按天数范围过滤。
- 三个维度：全体请求（`days`）、模型 × 日期（`models`）、
  账号 × 日期（`accounts`）。
- 落盘与导出**只含聚合数字、账号标识与模型名**，
  **不含消息正文或认证信息**。
- 另有"账号 × 模型 × 日期"一层，是**计费归属回填的唯一依据**。

**适用版本**：本页核对于 1.0.46。

### 8.2 ★ 模型名必须归一成**裸名**（所有者逐字要求）

> 「不要再把 平台:模型名 这种类似的 单独列一个统计了,这是错误的」

**现场证据**：`国服:deepseek-v4.1-flash` 记了 12 tokens / 1 次，
而 `deepseek-v4.1-flash · 国服` 记了 **1.6B / 4014 次** ——
**同一份用量被前缀拆成了两行**。

**规格**：

- 切分规则：无冒号 → 原样；3 段（平台:区域:模型）→ 取第 3 段，
  为空则退第 2 段；2 段 → 取第 2 段；**切完为空则原样返回**
  （宁可不切，也不能把模型名抹成空串）。
- **区域/平台信息由另一条通道承载，模型名只留裸名。**

**适用版本**：1.0.x 全线（本页核对于 1.0.46）。

### 8.3 ★ 模型名再按**大小写不敏感**归一

**现场（2026-10-05）**：所有者原话「一样的模型居然还分了两条记录」——
截图里 `GLM-5.3-Flash · ZCode`（11.0M / 98 次）与
`glm-5.3-flash · ZCode`（1.6K）**并排两行**。

**根因**：上游目录里的规范名是大写写法，而客户端发的是小写；
两者去掉前缀后**逐字**落键。而本仓**其它所有**模型比较都是大小写不敏感的
—— 只有用量统计这一处逐字比较，**那是遗漏而不是设计**：
路由认它们是一个模型，账单却当成两个。

**规格**：

- 归一策略是**沿用已存在的那个拼写**（忽略大小写地找），
  找不到才用本次传来的写法。
- **不一律转小写**：模型**显示名**要尽量稳定。一律转小写会让历史里那份
  大写写法在界面改名，而 `/v1/models` 目录里仍是大写 ——
  两处对不上又多一个新困惑。沿用已有写法只在"首次见到该模型"时定型。
- **已落盘的历史由载入时的自愈合并**（实测 8 → 6）。
- ⚠ **查找范围必须是全部四张表**，不能只看"模型"那张：
  一份被截断/手改过的文件完全可能只在别的表里留下键；
  若只看一张，写入路径会用新写法落键，而装载自愈按旧写法合并 ——
  两边打架，同一个模型**又裂开**。

**适用版本**：1.0.27（2026-10-05）起。

### 8.4 计费行平台归属

- 计费行的平台归属按**计费键**回填；旧口径按账号标识形状**猜**，
  重启后分布会漂。
- 另有修复：**积分幻影记录**（"-380 然后 +380"的幻影配对）、
  账号库**重复条目去重**（同一账号存两条会导致"禁用了但状态不显示、
  也无法启用"）。

**适用版本**：1.0.27 起（本页核对于 1.0.46）。

### 8.5 用量页的展示口径

- **不再截断成前 5 条**：此前 8 个账号都在正常轮转、界面只显示 5 个，
  会被**误读**成"负载均衡只用了 5 个账号"。
- **点账号/模型筛选时，左侧数字随筛选对象变化**
  （原口径下点了没反应，看起来像坏了）。
- 账号下拉与用量列表的取名口径为「**备注 → 昵称 → 标识前缀**」
  （原为"昵称 → 标识前缀"，于是**填了备注等于白填**）。

**适用版本**：本页核对于 1.0.46。

### 8.6 Token 统计的四个来源独立统计

WorkBuddy / WorkBuddy AI（国际版）/ CodeBuddy CLI / CodeBuddy CN IDE
**四个来源独立**统计输入、输出、缓存读写、调用次数。

### 8.7 官方用量与积分统计

- **官方用量**：每日趋势、模型分布、账号消耗、请求明细（逐条可查）。
- **积分统计**：积分变动记录（领取、消耗、过期逐条留痕）、
  到期监控（7 天内到期高亮并优先排序）、
  统一记录视图（签到日志 / 积分统计 / Token 统计三处**口径一致**）。
- **国际版账号的官方用量与积分查询走国际版域名**，
  不再误发国服域名被拒。
- **国服账号"消耗积分"曾恒为 0**（实测 15 个国服号整列 0、12 个国际版正常）：
  根因是计费后台的 WAF 拒绝"看起来像裸 API 客户端"的请求 ——
  实测只带基础头会回 `403 code=10085`，**再加
  `X-Client-Platform: web` / `Referer` / `User-Agent` 任一**即 200。
  修后实测积分从 0 变成真实值、到期日从空变成真实日期。

**适用版本**：国服积分恒 0 修复于 **1.0.35**（2026-10-08）。

### 8.8 账号池「正在使用」与冷却的可观测性

- 状态列显示「**使用中 N**」（N = 该账号此刻的在途请求数）并给整行加左色条；
  空闲账号显示「**N 分钟前用过**」。**不展开就能看出流量落在哪个账号上**。
- 两类冷却**分开显示**：账号级冷却（整号不可用）与模型级冷却
  （仅这几个模型不可用、换模型仍可用），后者用角标计数 + 悬浮明细。
- 「排队中」的口径必须与选号**完全相同**：
  新导入或持续失败的账号同样是"从没用过"，但它们**不是排队**。
  口径不一致会把"真正在服务的账号"全标成"排队"。

**适用版本**：本页核对于 1.0.46。

## 9. 界面约定

### 9.1 shadcn 组件优先（仓库强制约定）

- 前端 UI **优先复用项目已有的 shadcn 组件**，先组合，再考虑自写交互原语。
- 缺组件时**补上对应的 shadcn / Radix 组件**并包在统一目录下，
  以保持样式、无障碍、焦点管理与行为一致。
- **只有** shadcn 及其组合 API 无法满足需求时才写自定义组件，
  且必须**先记录原因**。
- 自定义 UI **仍必须**复用项目的 **Rhea 主题令牌**、间距、圆角、状态与无障碍约定。
- ⚠ **不得**用原生交互捷径（如 `details`/`summary`）替代已有的 shadcn 组件。

**适用版本**：2026-09-12 起生效（本页核对于 1.0.46）。

### 9.2 主题令牌要收敛，不要就地硬编码

已知的两次教训：

- 某处状态色因为"无法统一调整，也与 Rhea token 体系脱节"，
  后来才**收敛成统一的警告令牌**。
- 深色模式靠 **CSS 变量**切换，**不靠组件内写死的颜色**。

**含义**：新增状态色/语义色时，先找**已有令牌**；
找不到再新增令牌，**不要**在组件里写死色值。

**适用版本**：本页核对于 1.0.46。

### 9.3 前端状态与导航的三条已定行为

- **页面切换保持状态缓存**：三级视图进 URL，返回时状态不丢。
- **平台面板互斥显示**（曾是真产品缺陷：非选中面板**永不隐藏**）。
- **启动期限流**：前端限流 4 并发 + 批量接口 + 缓存预热。
  实测 A/B：API 调用 **167 ⇒ 45**、最慢 **27,412 ms ⇒ 2,717 ms**、
  长任务 **0**。

**适用版本**：1.0.25 / 1.0.26 / 1.0.20 ⑩（本页核对于 1.0.46）。
