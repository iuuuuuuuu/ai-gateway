## D01 · 网关从 Go 全量重写为 Rust，走「多产品等价」路线（2026-10-01 定案 · 1.0.14 起）

**结论**：网关内核重写为 `crates/ai-gateway-router`（Rust），产物
`target/<profile>/gateway.exe`。重写按「**多产品等价**」进行：Qoder / ZCode /
Trae 的能力在 Rust 侧**逐项保留**，不做功能裁剪。

**背景**：1.0.13 时上游 `momo0410/ai-gateway` 的 PR#2 已经把 Go 网关删掉、换成 Rust，
并且**不接 Qoder**（ZCode 只作为「可导入的客户端」）。当时本仓库**选择不跟**，
只做定点摘取（`.github/RELEASE_NOTES_1.0.13.md` 第一节「保留未并的部分（有意）」）。
2026-10-01 业主改口径为「我们也换成 rust 全重写」，1.0.14 落地。

**排除的方案**：
- **整体跟随上游 PR#2 的路线**（删 Go 网关、不接 Qoder、ZCode 降级为可导入客户端）——
  那会丢掉 8,448 行 Qoder 与 15,803 行 ZCode 的既有能力，是**功能倒退**，不是迁移。
- **保留 Go/Rust 双实现并行**——两套流式栈、两套超时语义，长期成本高于一次性重写。

**★ 代价（重写真实付过的学费）**：Rust 版搬了**实现**、丢了**接线** ——
Go `main.go` 的启动期接线（CLI 子命令拦截、三个后台循环）全在 **HTTP 面之外**，
所以 43 项 HTTP 验收**一条都抓不到**。症状是「Qoder 定时领取不触发」
「ZCode 自动领取完全不跑」「CLI 子命令让界面卡死」。可复用的排查方法记在
`.github/RELEASE_NOTES_1.0.14.md` 第二节：**把 Go `main.go` 的启动接线清单与
Rust `bin/gateway.rs` 逐条对差**。

**翻案条件**：不翻案。重写已完成、构建链已无 Go 依赖；除非出现 Rust 侧无法解决的
硬阻塞（例如某上游 SDK 只有 Go 实现），否则不回到 Go 主线。

## D02 · Go 参照实现留在仓库，但退出构建链；交叉编译一并取消（2026-10-01 起 · 1.0.14 起）

**结论**：`go-gateway/` **保留在仓库里**，但**不参与构建**。构建链上三处都已切断：
`build-gateway.{sh,ps1}` 不再调用 `go build`；三个 workflow 全部走
`sh scripts/build-gateway.sh`；`actions/setup-go` 从 `ci.yml` / `release.yml` 删除。
**交叉编译同时取消**：脚本收到 `GOOS`/`GOARCH` 时只打一行提示后**忽略**。

**背景**：
- 留 `go-gateway/` 的理由是它仍是一手对照物 —— `go-gateway/internal/zcode/CAPTURED-SPEC.md`
  由 Reqable 抓到的**成功请求**生成，被仓库约定为「上游协议细节的**唯一可信**规格来源」
  （见 `AGENTS.md`「参考实现的注释是二手信息」）。删掉它等于删掉这份规格。
- 取消交叉编译的理由是**故障面**：交叉编译需要为目标三元组装 std 与链接器，
  而 CI 四腿的 host 与 target 本来就一致（windows-latest→msvc、
  macos-14→aarch64-apple-darwin、macos-15-intel→x86_64-apple-darwin、
  ubuntu-22.04→x86_64-unknown-linux-gnu）⇒ 本机产物就是需要的产物，
  保留交叉只会引入「三元组没装」这一类新故障。

**排除的方案**：删掉 `go-gateway/`（丢掉一手规格来源）；以及「保留 `GOOS`/`GOARCH` 支持」
（维护一条 CI 从不走的路径）。

**翻案条件**：
- 真要交叉编译时，**不能只设环境变量** —— 必须在 workflow 里显式
  `rustup target add` 并配好链接器，否则得到的是「三元组没装」而不是产物。
- `go-gateway/` 只有在 `CAPTURED-SPEC.md` 被迁移进 Rust 侧并被同等信任后，
  才可以考虑移出仓库。

## D03 · 桌面应用与网关同进程树，网关 gzip 内嵌进主程序（1.0.0 起 · 现行 1.0.46）

**结论**：用户只拿到**一个** `ai-gateway.exe`。构建期 `build.rs` 把网关二进制
gzip 压缩后放进 `OUT_DIR`，`gateway_embed.rs` 用 `include_bytes!` 编进主程序；
运行时首次启动解压到 `%USERPROFILE%\.wb-switch\gateway\bin\gateway-<指纹>.exe`。
**网关是主程序的子进程，且被宿主 Job Object（`KILL_ON_JOB_CLOSE`）托管** ——
主程序死，网关被系统连带回收，不留孤儿。

**背景**：需求是「一个安装包、一个界面、一个进程树」。附带解决了一个真实缺陷类：
**「新功能在开发机上好好的，装完却没有」** —— 根因是 `build.rs` 会无条件内嵌
`embedded/gateway.exe` 里当时躺着的那一份，而 `build-signed.ps1` 一度从不构建网关。
现在的约定是 `build-signed.ps1` 的 `[3/4]` 步**强制重建**网关，并做构建前后
SHA256 指纹比对。

**为什么落地文件名带指纹**：指纹 = 「内嵌数据长度 + 内容哈希」。升级后指纹变化
⇒ 落到**新文件**，不会复用旧版本网关；同时避免反复覆盖同一文件导致杀软反复扫描。
它还是「正在跑的网关是不是本构建释放的」的**唯一判据** —— 正在跑的进程读不出
自己内嵌的指纹，但**文件名**里带着它（升级后自动换掉旧网关靠的就是这条）。

**★ 已知取舍（不修）**：`fingerprint()` 里的 FNV-1a 质数写成了
`0x1000_0000_01b3`（标准值是 `0x100000001b3`，多一个 0）。**不修** ——
指纹只用于缓存文件名与 `cleanup_old()` 的保留判定，仍然稳定且对内容敏感；
改质数会让所有用户的落地文件名变化、触发一次无谓重写。
⚠ 写断言脚本时要**照源码口径复算**（长度段是 **gzip 载荷**长度，不是解压后的 exe 长度）。

**排除的方案**：把网关作为**独立文件**随包分发（用户要管两个文件、版本易错配）；
以及「运行时下载网关」（离线不可用、且引入新的失败面）。

**翻案条件**：出现「同一台机器要同时跑多个不同版本网关」的需求时 ——
那时需要显式实例隔离，而不是靠指纹文件名。

## D04 · 数据目录回到 `.wb-switch`，但环境变量名刻意不改（2026-09-16 · 1.0.0 更名之后）

**结论**：数据目录是 `%USERPROFILE%\.wb-switch`；`.ai-gateway` **不再被写入**，
仅作为一次性迁移来源。环境变量**仍叫 `AI_GATEWAY_HOME`**，不随目录改名。

**背景**：1.0.0 更名时把数据目录换成了 `~/.ai-gateway` 并做一次性「复制式迁移」。
但 2026-09-16 起本仓库与老仓库（`workbuddy-switch-gateway`，0.8.x 线）**并行维护**、
两版会同时装在一台机器上，于是迁移暴露出一个真实的数据缺陷：

> 迁移的幂等标记 `.migrated-from-wb-switch` 让迁移**只跑一次**，此后 `.ai-gateway`
> 就成了迁移那一刻的快照。用户在任一版本里新增的账号都不会出现在另一个版本里 ——
> 而从用户视角这是**同一个应用的两代**，理当共用同一份账号库。

**为什么环境变量名不改**：它是**新版本才引入的**，改名只涉及源码；
改了反而会让既有的隔离脚本失效。⇒ 改名收益为零、代价是破坏已存在的自动化。

**迁移语义**：**复制式**（旧目录原样保留，可随时回退）；
**设了 `AI_GATEWAY_HOME` 时不迁移** —— 那说明用户在刻意隔离（开发/测试实例），
把真实用户数据搬进去反而会污染隔离环境。

**排除的方案**：继续用 `.ai-gateway` 并靠「双向同步」维持两版一致（要写一个
永不收敛的同步器）；以及「把环境变量一并改名」（纯破坏性变更）。

**翻案条件**：老仓库（0.8.x 线）停止维护、且不再有用户在两版之间来回切换时，
可以删掉迁移分支；环境变量名**仍不建议改**。

## D05 · 账号库是唯一真源，网关凭证是派生素材（1.0.0 起 · 现行 1.0.46）

**结论**：`%USERPROFILE%\.wb-switch\accounts.json` 是**唯一真源**；
`%USERPROFILE%\.wb-switch\gateway\gateway_auths\` 是**派生素材**，
删掉可自动重建。

**背景**：两个存储的**格式不同** —— 时间戳单位分别为毫秒与秒，字段集也不同
（账号库含 `profile_raw`、`auth_raw` 等客户端字段）。网关是**独立进程**，
需要自己能读懂的凭证目录。因此不合并，而是由自动同步机制保持一致。

**同步规则（有意不对称）**：
- 账号库 → 网关：按 uid 生成嵌套形凭证；账号删除或模式切换后自动清理残留
- 网关 → 账号库：网关自身刷新 Token 后，按**过期时间较新者**回写；
  **空 refresh token 不覆盖已有值**
- 内容无变化时不写盘 —— 避免无意义的文件时间戳变动与网关重启

**排除的方案**：让网关**直接读 `accounts.json`**（网关要跟着宿主的字段演进走，
宿主一改字段网关就崩；且网关需要的秒级时间戳与嵌套形状要现场换算）。
这个方案看起来省一层，实际把**两个进程的耦合面**从「一个文件格式」放大到
「宿主内部数据结构」。

**翻案条件**：网关与宿主合并成同一进程时（那时「两个进程各自要读得懂」这个前提消失）。

## D06 · 思考档位：网关**不预校验**，只如实转达上游的拒绝（2026-09-18 · 1.0.x 起）

**结论**：网关对 `reasoning_effort` **不做任何网关侧校验**，原样透传给上游。
上游若拒绝，**如实转达**：状态码用上游的真实状态（400，**不是 503**），
错误码**单独成型**（Chat 协议为 `reasoning_effort_rejected`），消息**带上上游原文**。

**背景**：`go-gateway/internal/server/forward.go` 的注释记着这次翻案的完整过程 ——
原实现是「客户端指定的档位不在该模型 `supportedEfforts` 里 ⇒ 400 拒绝」，
前提是「`supportedEfforts` 是该模型的**硬范围**」。实测推翻了它：

| 模型 | 上游声明 | 实测被接受的档 |
|---|---|---|
| `hy3` | `[low, high]` | medium / max / minimal / **off** 全部接受 |
| `glm-5.2` | `[high, xhigh]` | low / max / medium / **off** 全部接受 |

⇒ `supportedEfforts` 描述的是「界面上建议列出哪些档」，**不是**「只接受这些档」。
据它拦截会**误拒上游本来接受的合法请求**，而且用户拿到 400 后毫无办法（他用的档其实能用）。
**这类误拒比静默降级更糟。**

**与整合版的有意分歧**：`momo0410/ai-gateway` 对不被支持的档位做**静默降级**
（改写为最接近的支持档，只在日志留一行）。本仓库改为**直接拒绝**并让问题立刻可见。
理由是：档位是客户端**显式**指定的，悄悄改写会让用户看到「我明明调了 max，
回答却很短」——既不知道发生了什么，也不知道该改成哪个档，只能反复试。
两种做法各有取舍：静默降级对「客户端从别处抄来一个档位名」更宽容，直接拒绝则让问题立刻可见。
**本仓库选了后者。**（⚠ 整合版那一侧的原始行为**未证**：`momo0410/ai-gateway`
2026-10-06 已 404，无法回源核对；此处引用 `README.md` 的记载。）

**排除的方案**：
- 网关侧按 `supportedEfforts` 预校验（上面的实测已推翻其前提）
- 静默降级（让「调了 max 却没生效」不可见）
- 把档位拒绝混进 `no_healthy_account` 的 503 里（会把用户引去查账号，
  而真正的原因在请求里）

**★ 已知残余**：Rust 侧 `upstream/payload.rs` 里**仍保留**一个
`normalize_reasoning_effort()`（按 `supportedEfforts` 降级）。它唯一的**生产**
调用点是 `upstream/client.rs` 的 `prepare_body()`，而那里传的 `efforts` 是
**`None`**（`None` = 未知 ⇒ 不降级）⇒ **生产路径上它是惰性的**，只有单测会喂它数据。
⇒ 保留它是**死代码风险**：任何人将来把能力表接上去，D06 的结论会被无声推翻。

**翻案条件**：上游开始提供**结构化**的「本模型接受哪些档」查询接口（而不是
`supportedEfforts` 这种建议性字段）时，可以恢复预校验 —— 但那时错误码要保留
「单独成型 + 带上游原文」这两条，它们与预校验是否启用无关。

## D07 · 兜底清单不能参与「声明」竞争：猜测永远不该赢过事实（2026-09-22 · 1.0.x 起）

**结论**：模型清单分**两份**，语义严格区分：

| 字段 | 来源 | 参与 |
|---|---|---|
| 宿主透传清单（上游**真实查询**） | 宿主 | 「不排除」**+**「声明」 |
| 网关内置静态表（**猜测**） | 网关 | **只**参与「不排除」 |

即「不知道某产品提供什么 ⇒ **别排除**它，但也**别声称**它提供」。

**背景**：`GLM-5.3` / `Auto` 这类**多个平台都提供**的模型报
`400 model_not_in_region`，而只被单一平台提供的模型正常 —— **差别就在「重叠」**。
根因：`productDeclaresModel` 一开始只看宿主透传的清单（可信）；
后来为了修「裸名模型被路由到 WorkBuddy」，补了一份内置静态表作为 workbuddy 的兜底，
当时的注释写着「它是『声明』用的，不是『否定』用的 —— 多列几个不会让任何账号失去资格」。
**那句话在引入 `declared` 优先逻辑之后就失效了** —— 兜底清单一进 `declared`，
workbuddy 就与真正提供该模型的平台**竞争**，而它账号多 19 倍 ⇒ 压倒 ⇒
选中其实没有该模型的账号。

**★ 可复用的判据（加任何「补全清单」逻辑前先问）**：
> **它会被当成声明吗？** 若会被当成声明，就必须走 fallback 那条路 ——
> 猜测永远不该赢过事实。

**排除的方案**：把静态表直接并进可信清单（就是上面那个缺陷）；
以及「干脆不用静态表」（会让静态表覆盖的模型在观测集为空时全部不可选）。

**翻案条件**：上游提供「按产品查询模型清单」的**权威接口**、且能覆盖全部产品时，
静态表可以整体退役 —— 那时 `fallback` 这条通道自然消失。

## D08 · 例外：Trae 的兜底清单是**权威**的，可以硬排除（2026-10-07 · 1.0.33）

**结论**：新增 `product_fallback_authoritative` 标记「哪些产品的兜底清单是权威的」。
**只有 Trae 进这个集合**（注入点 `bin/gateway.rs`）。对权威产品，兜底清单
**可以参与硬排除**。

**背景**：D07 把「静态兜底清单没命中」从「确定没有」降级成「**猜测**」
（`guess_excluded`）之后，**27 个 WorkBuddy 号 + 1 个 Trae 号一起进了抽签池**
⇒ 约 1/32 ≈ 3% 抽到那个 Trae 号（Trae 上游确实没有 `space-bunny`）⇒ 400。

**为什么 Trae 可以例外**：它的兜底清单**不是猜测** —— 派生自
`products/trae/dispatch.rs` 的 `ALIASES` 表（58 条客户端名 → 18 个上游
`config_name`），仓库文档原文称它是 Trae 模型名的「**唯一**真相」。
⇒ 对 Trae 而言它就是**确定**；而 WorkBuddy 的静态表是 2026-09-18 快照，才是真正的猜测。

**教训（比结论更值钱）**：D07 与 D08 合起来是一条完整口径 ——
「**猜测 vs 权威**」不是一个全局开关，而是**逐产品**的属性。
把两者混为一谈，两个方向都会错：混成「都权威」⇒ D07 的抢号；
混成「都猜测」⇒ D08 的 3% 抽错平台。

**排除的方案**：把「权威性」做成全局布尔（就是上面两种错的合体）。

**翻案条件**：Trae 的 `ALIASES` 表不再被上游真实清单覆盖/校对时，
它的「权威」资格要重新评估 —— 判据是「这张表最后一次与上游对齐是什么时候」。

## D09 · 熔断不是「停服」：单账号产品必须在**同产品内**兜底（2026-09-22 · 1.0.x 起）

**结论**：`pick_for_model_product_region` 在「该产品**一个健康号都没有**」时，
退到**同产品内部**的冷却兜底。**兜底绝不能跨产品。**

**背景**：`qoder:` 前缀的请求**全部 503**，而 zcode 与账号名都正常。
根因：上游 5xx 连续 3 次触发熔断 **30 分钟**，而产品前缀请求的候选集**锁死了 product**，
严格路径又刻意不兜底 ⇒ 该产品只有 1 个账号时**彻底不可用 30 分钟**。

**取舍的实质**：熔断的语义是「这个号可能不好，**换个号**」——
当该产品**没有别的号可换**时，熔断只是把一次**上游瞬时故障**放大成**停服**。
宁可拿「可能不好」的号试一次（上游已恢复 ⇒ 成功；仍故障 ⇒ 用户看到
**真实上游错误**而非误导性的「所有账号不可用」）。

**两条不许破坏的边界**：
- **兜底只在「确实一个健康号都没有」时触发** —— 有健康号时严格路径已返回，
  兜底分支根本不执行 ⇒ **多账号产品的熔断保护不受影响**。
- **绝不跨产品**：`qoder:` 是用户的**显式指令**，把 WorkBuddy 账号拿给它用
  会拿错凭证、打到错的端点。

**排除的方案**：让产品前缀也走通用兜底（跨产品拿错凭证）；
以及「产品只有一个号时就不熔断」（把熔断保护整个让掉）。

**翻案条件**：不翻案。这是**语义修正**，不是可调参数。
若某产品确实需要「单号也不兜底」，那应做成**显式开关**，而不是改这里的默认。

## D10 · 并发上限：每账号 3 + **换号重试**（2026-09-22 定值 · ★ Go 的「排队」语义未随重写保留，**未决**）

**结论**：`pool.max_in_flight = 3`（**每账号**上限，三个产品统一）。
名额满时 `Pool::acquire()` **返回 false**，调用方**换号重试**。

**背景**：症状是「同一个模型、同一个网关 —— 用 `curl` 发**每次都成功**，
但客户端**每次都失败**（`503 no_healthy_account`）」。根因是客户端的 LLM 层会
**并发重试**：DSH 用的 `@earendil-works/pi-ai` 带 `retryProviderRequest`，
默认**重试 5 次**，**每个重试是独立的并发请求**。而 `max_in_flight` 是**每账号**上限，
qoder / zcode **各只有 1 个账号** ⇒ 该产品的总并发 = 这个上限。

**值的历史（每次都是实测驱动）**：`3 → 32 → 8 → 16 → 3`。
- `32`：**恰好压在 qoder 上游的并发天花板（≈30）上** ⇒ 一重试就越界。
  **教训：上限不能设成「刚好等于上游能力」** —— 网关自己的巡检/保活也占在途名额，
  必须留余量。
- 回到 `3`：因为**每账号** 3 在 19 个 WorkBuddy 账号上就是总并发 57，够用。

**★ 未决的行为漂移（必须写下来）**：Go 版当年**敢用 3** 的前提是
**名额满时排队等待**（`server.Config.InFlightWait` 默认 3000ms / `pool.AcquireWait`）。
Rust 版**没有实现排队**：`in_flight_full()` + `acquire()` 满额直接返回 false，
唯一调用点 `forward.rs` 是**换号重试**。
⇒ 对**单账号产品**（qoder / zcode）「换号」无处可换，**正是「并发重试成片 503」
的成因形状**。而 `crates/ai-gateway-core/src/modules/gateway.rs` 里那段
「为什么现在敢用 3」的说明是 **Go 时代遗留**（引用的 `InFlightWait` / `AcquireWait`
在 Rust 侧只存在于注释里，**没有任何实现**）。

**排除的方案**：把上限开大（治标 —— 真正的问题是「满了之后怎么办」不是「上限多少」）；
以及「把上限设成刚好等于上游能力」（上面 32 的教训）。

**翻案条件（两条，任一成立就该动手）**：
1. **再次出现「并发重试成片 503」，且已排除上游故障** ⇒ 把「排队等待」补回 Rust 侧，
   而不是继续调这个数字。
2. 单账号产品（qoder / zcode）开始承载真实并发流量时 —— 那时「换号」这条路
   在定义上就是死的。

⚠ 这条**需要 Owner 定夺**：保留换号，还是补回排队。**在定夺之前不要凭感觉改这个 3。**

## D11 · 流式 `finish_reason` 只能出现一次（2026-09-22 · 1.0.x 起）

**结论**：转发上游的 `finish_reason` 时记下「**已经给过**」，收尾时
**只在没给过时**才补一帧。**只有非空的 `finish_reason` 才算「给过」。**

**背景**：症状是「**内容已经出来了**（模型答对），但界面一直转圈，随后报错重试」，
业主现场原话是「**zcode 没问题、qoder 不行**」。
根因：`qoder/stream.go` 的收尾逻辑**无条件**补一个 `finish_reason: "stop"` 的收尾帧，
而 qoder 上游**自己也会**在最后一个内容分片里给 `finish_reason`（代码里原样转发）
⇒ **同一条流里出现两次**。实测（同一时刻、同一网关）：
`qoder:Qwen3.8-Flash` 出现 **2 次** ❌，`zcode:GLM-5.3-Flash` 出现 1 次 ✅。

**为什么仍要保留补帧路径**：上游只发内容、始终不给 `finish_reason` 时，
不补会让客户端**一直等** —— 那是 `finishFrame` 原本要修的缺陷。
⇒ 正确的形状是「**记状态 + 条件补**」，不是「不补」。

**⚠ 空帧陷阱**：上游偶尔发 `"finish_reason": ""` 的空帧。
把它当结束信号会让客户端一直等 ⇒ **必须判非空**。

**排除的方案**：无条件补帧（就是本缺陷）；以及「完全不补帧」（客户端一直等）。

**翻案条件**：不翻案。这是协议层的**幂等性要求**，不是取舍。
上游若开始保证「必发且只发一次 `finish_reason`」，补帧路径可以简化成
「仅在 EOF 前未见时补」，但**判据仍要保留**。

**★ 排查这类「只有某个平台不行」的方法（值得复用）**：把两者的**帧结构并排 diff** ——
数出 `finish_reason` 一个 2 次一个 1 次，根因立刻清楚。**比读代码猜快得多。**

## D12 · 上游已宣告完成时，不再把「只差 `[DONE]`」判成本轮失败（2026-10-07 · 1.0.34 起）

**结论**：`SseFramesIter` 新增 `saw_finish_reason` 状态位。
读错误分支里若 `saw_finish_reason` 为真 ⇒ **补一帧纯 `[DONE]` 正常收尾，不补 error 帧**。

**背景**：上游的收尾顺序是「**先**宣告 `finish_reason`、**后**写终止字节 `[DONE]`」，
而两者之间那一瞬恰是**连接最容易被掐断**的位置。旧判据只看 `[DONE]` ⇒
「内容已完整、只差 `[DONE]`」落进 else ⇒ **把一份写完的回答判成本轮失败**
（网关补 error 帧 ⇒ 客户端显示「本轮运行失败」⇒ 整轮重新生成）。
业主原话：「对话过程中对话会输出完就中断，**这是我为什么回退版本的原因**」。

现场取证：`gateway.log` **16 条**「上游流读取失败…`saw_done=false`」
（**全部是国际版账号**，已收 29,628–1,992,314 B）、插件日志 **18 次**
`upstream stream truncated (openai) — emitting in-band error`、
失败率 **16/13,780 ≈ 0.12%**、断流集中在**请求发出后 32 ms – 6 s**
且**多会话几十到几百毫秒内齐断** ⇒ 是**共享通道（代理/链路）抖动**，与账号、模型无关。

**★ 这是一次「单向放宽」，不是全面兜底** —— 三条边界都不许动：
- **首帧之前就断**（一个 token 都没交付）仍走 503 + 换账号重试
- **真截断**（吐了半句、从没宣告完成）仍报错
- **失败语义的 `finish_reason`（`"error"`）不算「给过」** ——
  上游会用**正常帧的形状**宣告失败（HTTP 200 + `choices[0].finish_reason:"error"`，
  帧里**没有** `error` 字段）。把它当完成会让客户端拿到一个假的正常收尾。

**为什么值得放宽**：客户端整轮重试 = **重新生成一遍**，比丢掉一个终止字节昂贵得多。

**排除的方案**：继续只看 `[DONE]`（就是本缺陷）；
以及「任何读错误都当正常收尾」（会把真截断吞掉，用户拿到半截回答却没有错误提示）。

**翻案条件**：上游改成「**先**写 `[DONE]`、**后**宣告 `finish_reason`」，
或提供显式的「本轮已完成」信号时，这条例外可以收回 —— 但**必须先有实测**证明
新顺序成立（`AGENTS.md` 的规矩：改动上游协议细节前先读抓包规格，
参考实现的注释可能过时或针对别的通道）。

## D13 · 签名密钥固定在仓库外，且**刻意不自动搬运**（2026-09-19 实测校准 · 1.0.x 起）

**结论**：签名私钥与口令放在**仓库之外**；`build-signed.ps1` 的 `Resolve-KeyPath`
按**首选 → 回退**解析：
1. **首选** `%USERPROFILE%\.wb-switch\wb-switch-updater.key` / `.password`
2. **回退**（1.0.0 / 1.0.1 更名那一代）`%USERPROFILE%\.ai-gateway\ai-gateway-updater.key` / `.password`

走回退路径时脚本打印**黄色提示**，**但绝不自动搬运私钥**。

**背景**：私钥**不入库**（`.gitignore` 排除 `*.key` / `*.key.pub`）。
在公开仓库里，被 git 跟踪的文件里出现口令是**不可撤销**的泄露 ——
即使随后删除，历史里仍然在。

**为什么不自动搬运私钥**：脚本注释写明了理由 ——
> **私钥丢失即无法再为已发布客户端签名。**

自动搬运会引入「搬运中途失败 / 只搬了一半 / 覆盖了目标位置已有的另一把密钥」
这些**不可恢复**的路径。**宁可多一条回退分支，也不自动搬私钥。**

**★ 必须承认的代价（口径已分叉过）**：实际密钥放在**仓库根的同级 `keys\` 目录**
（即仓库之外，`.gitignore` 已排除 `*.key` / `*.key.pub`）⇒ 脚本默认的两处路径
**在本机都不存在**，**必须**用 `-KeyFile` / `-PasswordFile` 显式指定：

```powershell
& ".\scripts\build-signed.ps1" -KeyFile "<密钥路径>" -PasswordFile "<口令路径>"
```

⚠ **`.github/workflows/release.yml` 头部注释里写的
`%USERPROFILE%\.ai-gateway\ai-gateway-updater.key` 是过时口径** ——
以 `build-signed.ps1` 的 `Resolve-KeyPath` 为准（首选 `.wb-switch`、回退 `.ai-gateway`）。
`release.yml` 里那句只影响「本地路径提示」，CI 走的是 secrets，不受影响。

**排除的方案**：
- 私钥入库（公开仓库 ⇒ 不可撤销泄露）
- 私钥自动从旧路径迁移到新路径（不可恢复的失败路径）
- 把口令写进任何被 git 跟踪的文件（含脚本注释与示例）

**翻案条件**：改用**硬件/系统级密钥库**（如 OS 凭据管理器 / 硬件令牌）时，
「路径解析 + 回退」这套可以整体退役 —— 但那时仍要保留
「**不自动搬运**」这条原则（换成「不自动导出」）。

## D14 · 仓库转为 private：以**应用内自动更新**为代价（2026-10-06 · 1.0.31 / 1.0.32 之后）

**结论**：仓库按业主指令转为 **private**。**代价是应用内自动更新彻底失效。**

**背景与事实链**：
- 客户端的 updater 端点是
  `https://github.com/iuuuuuuuu/ai-gateway/releases/latest/download/latest.json`
  （`src-tauri/tauri.conf.json` 的 `plugins.updater.endpoints` 第一项）
- 该仓库 2026-10-06 转为 private 后，**匿名**访问
  `releases/latest/download/latest.json` / `api.github.com/.../releases` / 仓库页
  **全部 404**
- `tauri-plugin-updater` 是**匿名 HTTP 拉取、不带任何凭据** ⇒
  **加 `Authorization` 头也救不了**，这不是配置问题
- 对照实测（同一台机器上的 A/B）：另一个私有仓库的同一路径匿名 = **404**，
  而同期的本仓库（当时 public）= **302** ⇒ 不是猜测

**影响面**：**包括业主自己桌面那一版** —— 端点写死在客户端里，
所以「用户点检查更新」这条路对**所有已安装的客户端**都断了。

**★ 诚实边界**：转 private 对安全**没有实质收益** ——
全量扫描 850 个 tracked 文件，`gho_[A-Za-z0-9]{20,}` / `Bearer [A-Za-z0-9._-]{40,}` /
`sk-[A-Za-z0-9]{16,}` **命中均为 0** ⇒ 仓库里本来就没有真 token / API key。
命中的 email 与 GUID 全是测试占位。

**排除的方案**：不转 private（业主的指令，非技术选项）；
以及「在客户端里内置凭据去拉私有 Release」（把凭据发到每个用户手里，
泄露面远大于收益）。

**翻案条件（恢复通道只有两条，二选一）**：
1. **仓库改回 public**
2. **把 `endpoints` 换成别的公开托管点**（自建静态站 / 对象存储 / 另一个公开仓库）

⚠ 只改 `endpoints` 而不改客户端**对已安装用户无效** ——
端点写死在已发布的客户端里。要让存量用户恢复，只能走**手动下载覆盖安装**。

## D15 · 版本积压与「服务端单文件产物不随 Release 发布」的口径（2026-10-14 / 2026-10-15 核对）

**结论**：两件事**相互独立**，不要混为一谈：
1. **1.0.39 ~ 1.0.46 尚未打 tag、尚未发 Release**（安装包都已产出并落在 `dist\`，
   只差推 tag + 发 Release）。已发布的 Release 到 **v1.0.38** 为止
   （`releases/latest` 与 `dist\latest.json` 现都还指向 v1.0.38）。
2. **服务端单文件产物**（`dist\ai-gateway_<版本>_server-x64.exe`）**历来手工产出**，
   `release.yml` **没有**服务端单文件构建步骤 ⇒ 它**不随 Release 发布**，
   因此**不需要**为它单独打 tag。

**背景**：口径混在一起会产生一个假问题 ——「服务端产物没发 Release，是不是漏了 tag？」
答案是**不是**：tag 缺口（第 1 条）与产物口径（第 2 条）是两件事。

**★ 为什么 tag 缺口能长期存在而不被发现（值得记的教训）**：
- **发版一直是手工做的** ⇒ 流水线红不红没人看
- 更早的一个同型缺陷：`ci` 与 `release` 两条工作流**从 v1.0.23 起一直红**，
  `release.yml` 的 preflight 挂在「核心单测」⇒ 四平台 build 与「发布 Release」
  两步**全被 skip**，**等于 tag 打上去什么都不会发生**。
  根因之一是被 gitignore 的 `test-bin/` 在 CI 上不存在（夹具指向它），
  另一个是平台/环境变量假设（`#[cfg(windows)]`、`C:\...` 路径、`LANG`/`TZ`）。
- **教训**：`test-bin/`、`dist/` 这类被 gitignore 的目录，会让
  「**本地全绿 / CI 全红**」长期共存而不自知。凡是被 `.gitignore` 排除、
  但**测试或构建依赖**的路径，都必须先问一句「**CI 上它从哪来**」。

**排除的方案**：把「不发 tag」当成省事（Release 是**唯一**的对外版本信号，
不发 = 用户永远停在 v1.0.38）；以及「为服务端产物也打 tag」
（会与桌面版 tag 语义冲突，且该产物从来不在 Release 通道上）。

**翻案条件**：
- 若要**恢复自动更新通道**（见 D14），必须先**补发 tag + Release** ——
  否则即使仓库改回 public，`releases/latest` 指向的仍是 v1.0.38。
- 若服务端单文件产物**改为随 Release 发布**，那时才需要为它设计版本口径
  （现在它靠**文件名里的版本号**与 `ai-gateway.exe version` 自证，
  且 PE 版本资源**全空**）。

## D16 · 发版前必须过测试门控：preflight 用 `needs` **拦住**发布（2026-10-09 查实并修复 · 1.0.38 起）

**结论**：`release.yml` 增加 **preflight** job（单个 ubuntu job）作为发版前的验证门，
四个平台 build job **必须等它通过**才开跑。用 `needs`（**能拦住**），
**不用** `continue-on-error`。

**背景**：`release.yml` 的注释原话 ——
> 本工作流此前**没有任何测试** —— 没有 cargo test、没有 cargo check、没有网关单测，
> 唯一的校验是产物断言（`.sig` 数量、安装包存在性）。也就是说，
> **一个 tag 完全可以为「从未通过编译校验与单测」的代码发布安装包，
> 而且发布一旦出去就撤不回来。** 这一点在 push 阶段由 `ci.yml` 覆盖，
> 但打 tag 时并不强制要求 ci 绿 —— **tag 可以打在任意 commit 上**。

**为什么是一个独立 job 而不是塞进四个平台 job**：那会把同样的检查重复跑 4 遍，
而 windows 那条关键路径已经很贵。用一个 ubuntu job 做门控，
四平台等它的代价只有 ~2 分钟，换来「**发布出去的必定测过**」。

**★ 与 build 的策略**是**相反**的，两者互不冲突（这一点最容易改错）：
- **preflight**：用 `needs` ⇒ **就是要它能拦住**发布
- **build**：用 `continue-on-error: true` + release job 的 `!cancelled()`
  ⇒ **单平台失败不阻断其余平台**，也不阻断 Release

⚠ 两个细节缺一不可（`release.yml` 注释明确写了）：`continue-on-error` 只保证
「本 job 失败不把整个 run 判为失败」；**release job 必须配合 `!cancelled()`**
才会在 build 失败时照常执行 —— 因为 `needs: build` 默认要求依赖成功。
只加 `continue-on-error` 而不改 release 的 `if`，仍然会出现
「一个平台挂了、整个 Release 一个资产都发不出来」（v0.7.1 就是这样）。

**★ 但 preflight 自己也有一处必须留意的边界**：`!cancelled()` 对「**被 skip**」
也是 true ⇒ 必须同时判 `needs.preflight.result == 'success'`，
否则 preflight 一挂、build 被 skip、release 照常执行却一个产物都没有，
轻则报错重则**发一个空 Release**。

**排除的方案**：不设门控（就是上面那个「tag 可以打在任意 commit 上」的漏洞）；
以及把检查塞进每个平台 job（4 倍成本）。

**翻案条件**：不翻案。**但门控的有效性依赖「tag 打在已通过 CI 的 commit 上」这条纪律**
—— 1.0.37 的 tag 就打在 CI 红的那次（其 release run 的 build / 发布两步是 skipped，
Release 是手工建的）。⇒ 发版前**先看 CI 是否绿**。

## D17 · 已知并接受的依赖告警：`glib` 0.18.5 不可升级，保持 open（2026-10-15 · 1.0.46）

**结论**：`Cargo.lock` 里的 `glib 0.18.5` 命中 GHSA-**wrw7-89jp-8q8g**
（medium，RustSec：`VariantStrIter` 的 `Iterator`/`DoubleEndedIterator` 实现不健全）。
**当前无升级路径 ⇒ 接受该风险，告警在 GitHub 上保持 open（不 dismiss、不 suppression）。**

**为什么会命中**：`glib` 只经 **Linux** 依赖链进入：
```text
glib ← atk ← gtk 0.18.2 ← libappindicator 0.9.0 ← tray-icon 0.24.2 ← tauri 2.11.5
```

**为什么升不动（三方同时钉死 `^0.18`；2026-10-15 逐环核实）**：

| 环 | 约束 | 可否升 |
|---|---|---|
| `gtk 0.18.2` | `glib = "^0.18"` | `gtk` 最高只到 **0.19.0**（要求 `glib ^0.22`，本可修） |
| `libappindicator 0.9.0` | `gtk = "^0.18"` | 已是最高版 |
| `tray-icon 0.24.2` | `gtk = "^0.18"` | **最新 0.26.1 仍写 `gtk ^0.18`** |
| `glib` | 修复版从 **0.20.0** 起 | `0.18.x` 最高就是 0.18.5，**无 backport** |

实测命令与输出（可复现）：

```powershell
cargo update -p glib --precise 0.20.12
# error: failed to select a version for the requirement `glib = "^0.18"`
#   candidate versions found which didn't match: 0.20.12
#   required by package `gtk v0.18.2` ... of package `tauri v2.11.5`
```

**为什么接受（两条把严重度压下来的事实，都是实测而非推断）**：

1. **Windows / macOS 目标根本不含 `glib`** —— `cargo tree -i glib --target x86_64-pc-windows-msvc`
   与 `--target aarch64-apple-darwin` 都返回 `warning: nothing to print`；
   **只有 `--target x86_64-unknown-linux-gnu` 才拉进这条链**。
   本产品主力分发平台是 Windows（见 D14/D15），暴露面限于 Linux 产物。
2. **漏洞 API 在依赖图里不可达** —— 问题函数是 `VariantStrIter` / `Variant::array_iter_str()`；
   对整个已下载依赖源码 `grep -rn 'VariantStrIter'`（排除 `glib` 自身定义）**外部调用点 = 0**；
   我们自己的代码 `grep -rn 'glib|gio::|VariantStrIter' src-tauri/src crates/*/src` **命中 = 0**。
   ⇒ 没有任何路径会走到那个不健全的迭代器。

**排除的方案**：
- **dismiss 告警**：会让面板变干净，但等于把「暴露面可能变化」这件事藏起来 ——
  而 Linux 产物仍在发布（`AI.Gateway_*_amd64.deb` / `.AppImage`，见 v1.0.38 的 Release 资产）。
- **自己 vendored 一份打过补丁的 `glib 0.18.5`**（改动只有 `&p` → `&mut p` 一处）：技术上可行，
  但要自维护一个补丁 crate，且**没有任何实测证据表明我们踩到了它**（见上「不可达」）。
  为一个不可达的缺陷引入长期维护面，不划算；**真出现真实崩溃再翻案**。
- **升 tauri 到 3.0 alpha**：其 `tray-icon ^0.25` 仍钉 `gtk ^0.18`，**不解决问题**，反而引入 alpha 风险。

**翻案条件（任一成立就动手，此时优先「本地补丁」）**：
1. `tray-icon` 或 `libappindicator` 换到 `gtk ^0.19` 及以上 ⇒ 直接升级即可修复；
2. 有实测证据表明 Linux 产物真的走到了 `VariantStrIter`（如 NULL 解引用崩溃栈里出现该函数）；
3. 决定**停止发布 Linux 产物** ⇒ 该链彻底离开依赖图，可同时关掉这条告警。

**⚠ 维护纪律**：这条**故意保持 open**。它**不是**回归、**不是**待办、**不是**假绿门禁 ——
看到它时**先读本条**，不要重复排查一遍依赖链（本次已把每一环查死）。
另外两条同批告警**已经修好**（`source-map-js` → 1.2.2、`rustls` → 0.23.45），不在本条范围内。
## 附：怎么用这份文档

### 什么时候该翻案

一条决策该被重新审视，只有**三类**触发条件：

1. **它的前提被实测推翻**。D06（`supportedEfforts` 不是硬范围）与 D11
   （`finish_reason` 出现两次）都是这样翻的 —— **不是有人觉得不好，是有实测数据**。
2. **它写下的「翻案条件」成立**。每条决策末尾那一段就是为此存在的；
   条件没成立就不要动。
3. **代价换了个方向**。D14 的代价（自动更新失效）是**当初就写明的**；
   若某天「自动更新」比「仓库私有」更重要，那是**业主的取舍**，不是技术判断。

**反过来说：不要因为「实现起来麻烦」「看起来旧」就翻案。**
这份文档里最贵的几条（D07 / D08 / D09 / D12）都是**用真实缺陷换来的**，
推翻它们的成本不是改几行代码，而是**重新踩一遍那些坑**。

### 谁有权翻案

| 类型 | 谁定 | 例子 |
|---|---|---|
| **产品口径 / 对外承诺** | **业主（Owner）** | D14 仓库可见性、D15 发不发版、D10 保留换号还是补回排队 |
| **协议正确性 / 不变量** | **实测数据** | D11 `finish_reason` 幂等、D12 单向放宽的边界 |
| **工程实现取舍** | 维护者，但**必须写回本文档** | D02 交叉编译、D03 指纹不修、D13 不自动搬私钥 |

**翻案的正确顺序**：
1. 先在**本文档**把该条改成新结论 + 注明**翻案日期与理由**（引用实测证据）
2. **再**改代码
3. 最后同步 `README.md` / `PROJECT-STATE.md` / `AGENTS.md` 里引用该结论的地方

**不要只改代码留下一条自相矛盾的记录** —— 本仓库已经有过这种代价。
