# Agent Note: 思考档位网关不预校验，只如实转达上游的拒绝

Status: implemented

## Problem

原 `docs/DECISIONS.md` D06（从 DECISIONS.md 迁移）。原实现对 `reasoning_effort` 做**网关侧预校验**：客户端指定的档位不在该模型 `supportedEfforts` 里 ⇒ 400 拒绝。这个实现的前提是「`supportedEfforts` 是该模型的**硬范围**」—— 实测把它推翻了：`hy3` 上游声明 `[low, high]`，实测 `medium` / `max` / `minimal` / **`off`** 全部被接受；`glm-5.2` 上游声明 `[high, xhigh]`，实测 `low` / `max` / `medium` / **`off`** 也全部被接受（完整对照表见 Verification）。

⇒ `supportedEfforts` 描述的是「界面上建议列出哪些档」，**不是**「只接受这些档」。据它拦截会**误拒上游本来接受的合法请求**，而且用户拿到 400 后毫无办法 —— 他用的那个档其实能用。**这类误拒比静默降级更糟。**

不修的话，任何「上游实际比声明更宽容」的模型都会稳定踩中，症状是「档位明明可用却被网关拦掉」，而排查方向会被指向客户端参数。

这次翻案的完整过程记在 `go-gateway/internal/server/forward.go` 的注释里。

## Decision

### 网关侧零校验，原样透传

网关对 `reasoning_effort` **不做任何网关侧校验**，原样透传给上游。判定「这个档行不行」的权力完全归上游。

### 上游拒绝时如实转达，不改造

上游若拒绝，网关**如实转达**，三条同时成立：

- 状态码用**上游的真实状态**（400，**不是 503**）；
- 错误码**单独成型** —— Chat 协议为 `reasoning_effort_rejected`；
- 消息**带上上游原文**。

### 与整合版 `momo0410/ai-gateway` 的有意分歧：拒绝 vs 静默降级

整合版对不被支持的档位做**静默降级**（改写为最接近的支持档，只在日志留一行）。本仓库改为**直接拒绝**并让问题立刻可见。

理由是：档位是客户端**显式**指定的，悄悄改写会让用户看到「我明明调了 max，回答却很短」—— 既不知道发生了什么，也不知道该改成哪个档，只能反复试。

两种做法各有取舍：静默降级对「客户端从别处抄来一个档位名」更宽容，直接拒绝则让问题立刻可见。**本仓库选了后者。**

⚠ 整合版那一侧的原始行为**未证**：`momo0410/ai-gateway` **2026-10-06 已 404**，无法回源核对；此处引用 `README.md` 的记载。

### ★ 已知残余：`normalize_reasoning_effort()` 的死代码风险

Rust 侧 `upstream/payload.rs` 里**仍保留**一个 `normalize_reasoning_effort()`（按 `supportedEfforts` 降级）。它唯一的**生产**调用点是 `upstream/client.rs` 的 `prepare_body()`，而那里传的 `efforts` 是 **`None`**（`None` = 未知 ⇒ 不降级）⇒ **生产路径上它是惰性的**，只有单测会喂它数据。

⇒ 保留它是**死代码风险**：任何人将来把能力表接上去，本决策的结论会被无声推翻。

## Alternatives considered

- **网关侧按 `supportedEfforts` 预校验（就是原实现）** — 它最强的理由是**它能在网关侧一次挡掉非法请求**：客户端立刻拿到明确错误，不必等一次上游往返，也不消耗账号配额与上游调用；而且当时的前提「`supportedEfforts` 是硬范围」看起来完全成立，实现也只需一次集合查找。否掉的原因是实测**推翻了那个前提** —— 它会误拒上游本来接受的合法请求，而用户拿到 400 后毫无办法。

- **静默降级（改写为最接近的支持档，只在日志留一行）** — 它最强的理由是**对客户端最宽容**：客户端从别处抄来一个档位名时不会撞上 400，请求照常成功，用户至少拿到了回答；实现上只需一次映射，且整合版 `momo0410/ai-gateway` 就是这么做的，有现成先例。否掉的原因是档位是客户端**显式**指定的，悄悄改写会让「调了 max 却回答很短」不可见 —— 用户既不知道发生了什么，也不知道该改成哪个档，只能反复试。

- **把档位拒绝混进 `no_healthy_account` 的 503 里** — 它最强的理由是**复用既有错误路径**：网关不必新增错误码、不必新增分支，客户端也已有 503 的处理与重试逻辑，改动面最小。否掉的原因是它会把用户引去查账号，而真正的原因在**请求**里 —— 误导方向比不报错更贵。

## Consequences

- **收益**：上游本来接受的档一定被接受，不再出现「合法请求被网关拦掉」；真被拒时用户拿到上游真实状态码、独立错误码 `reasoning_effort_rejected` 与上游原文，知道该改什么；错误码单独成型让客户端/日志可以精确判别这一类失败，而不是混在账号类错误里。
- **代价与已知上限**：客户端要多一次上游往返才知道档位不被接受（预校验本来能本地短路）；错误消息跟着上游文案走，上游改措辞则消息随之变化；`normalize_reasoning_effort()` 仍是**死代码风险** —— 谁把能力表接到 `prepare_body()` 上，本决策就被无声推翻，因此改那条路径前必须先读本篇。**重访信号（翻案条件）**：上游开始提供**结构化**的「本模型接受哪些档」查询接口（而不是 `supportedEfforts` 这种建议性字段）时，可以恢复预校验 —— 但那时错误码要保留「单独成型 + 带上游原文」这两条，它们与预校验是否启用无关。

## Verification

实测对照（推翻了 `supportedEfforts` 是硬范围这个前提）：

| 模型 | 上游声明 | 实测被接受的档 |
|---|---|---|
| `hy3` | `[low, high]` | medium / max / minimal / **off** 全部接受 |
| `glm-5.2` | `[high, xhigh]` | low / max / medium / **off** 全部接受 |

判据：不看声明字段，直接拿声明**之外**的档位打上游，看它是否真的拒绝。两个模型都接受了声明之外的档 ⇒ 预校验的前提不成立。
