# Agent Note: 上游已宣告完成时，不再把只差 [DONE] 判成本轮失败

Status: implemented

## Problem

原 `docs/DECISIONS.md` D12（从 DECISIONS.md 迁移）。上游的收尾顺序是「**先**宣告 `finish_reason`、**后**写终止字节 `[DONE]`」，而两者之间那一瞬恰是**连接最容易被掐断**的位置。旧判据只看 `[DONE]` ⇒ 「内容已完整、只差 `[DONE]`」落进 else ⇒ **把一份写完的回答判成本轮失败**（网关补 error 帧 ⇒ 客户端显示「本轮运行失败」⇒ 整轮重新生成）。

业主原话：「对话过程中对话会输出完就中断，**这是我为什么回退版本的原因**」。

现场取证：`gateway.log` **16 条**「上游流读取失败…`saw_done=false`」（**全部是国际版账号**，已收 29,628–1,992,314 B）、插件日志 **18 次** `upstream stream truncated (openai) — emitting in-band error`、失败率 **16/13,780 ≈ 0.12%**、断流集中在**请求发出后 32 ms – 6 s**，且**多会话几十到几百毫秒内齐断** ⇒ 是**共享通道（代理/链路）抖动**，与账号、模型无关。

## Decision

### 用 `saw_finish_reason` 状态位把「已宣告完成」和「没完成」分开

`SseFramesIter` 新增 `saw_finish_reason` 状态位。读错误分支里若 `saw_finish_reason` 为真 ⇒ **补一帧纯 `[DONE]` 正常收尾，不补 error 帧**。

### ★ 这是一次「单向放宽」，不是全面兜底 —— 三条边界都不许动

- **首帧之前就断**（一个 token 都没交付）仍走 503 + 换账号重试
- **真截断**（吐了半句、从没宣告完成）仍报错
- **失败语义的 `finish_reason`（`"error"`）不算「给过」** —— 上游会用**正常帧的形状**宣告失败（HTTP 200 + `choices[0].finish_reason:"error"`，帧里**没有** `error` 字段）。把它当完成会让客户端拿到一个假的正常收尾。

### 为什么值得放宽

客户端整轮重试 = **重新生成一遍**，比丢掉一个终止字节昂贵得多。

## Alternatives considered

- **继续只看 `[DONE]`（就是本缺陷）** — 它最强的理由是**判据单一、不可能误判**：`[DONE]` 是协议里唯一明确的终止字节，见到它才算完成，逻辑上没有「猜上游意图」的成分，也不需要新增任何状态位，实现与审查成本都最低。否掉的原因是上游的收尾顺序是「先 `finish_reason`、后 `[DONE]`」，两者之间那一瞬恰是**连接最容易被掐断**的位置 ⇒ 「内容已完整、只差 `[DONE]`」被稳定地判成本轮失败，现场 16 条日志 / 18 次 in-band error / 0.12% 失败率全是这一形状。

- **任何读错误都当正常收尾** — 它最强的理由是**彻底消灭这类误判**：既然读错误多半是链路抖动而非内容问题，一律当正常收尾就再也不会把写完的回答判成失败，也完全不需要 `saw_finish_reason` 这种状态位。否掉的原因是它会把**真截断吞掉** —— 用户拿到半截回答却没有错误提示，比报错重试更糟；这也正是本条只做「单向放宽」、并钉住那三条边界的原因。

## Consequences

- **收益**：链路在 `finish_reason` 与 `[DONE]` 之间的抖动不再被放大成整轮重新生成，收益是「省掉一次完整生成」这一量级；现场那 0.12%（16/13,780）的失败从「本轮失败」变成「正常收尾」。
- **代价与已知上限**：判据从一个字节（`[DONE]`）变成「状态位 + 三条边界」，正确性依赖 `saw_finish_reason` 只在**非失败语义**的 `finish_reason` 上置起 —— 若哪天把 `finish_reason:"error"` 也算成「给过」，客户端会拿到一个**假的正常收尾**，这比原来的缺陷更难发现。原文的翻案条件：上游改成「**先**写 `[DONE]`、**后**宣告 `finish_reason`」，或提供显式的「本轮已完成」信号时，这条例外可以收回 —— 但**必须先有实测**证明新顺序成立（`AGENTS.md` 的规矩：改动上游协议细节前先读抓包规格，参考实现的注释可能过时或针对别的通道）。这三个信号（顺序反转 / 显式完成信号 / 有人主张删掉边界）任一出现，就是必须重访该决定的时刻。

## Verification

- 现场取证（`gateway.log`）：**16 条**「上游流读取失败…`saw_done=false`」，**全部是国际版账号**，已收 **29,628–1,992,314 B**。
- 插件日志：**18 次** `upstream stream truncated (openai) — emitting in-band error`。
- 失败率：**16/13,780 ≈ 0.12%**。
- 断流时间分布：集中在**请求发出后 32 ms – 6 s**，且**多会话几十到几百毫秒内齐断** ⇒ 判为**共享通道（代理/链路）抖动**，与账号、模型无关。
- 业主原话（现场证据）：「对话过程中对话会输出完就中断，**这是我为什么回退版本的原因**」。
