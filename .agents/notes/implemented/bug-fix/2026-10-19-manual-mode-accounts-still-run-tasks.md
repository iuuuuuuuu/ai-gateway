# Agent Note: 手动模式下未勾选账号也要进池——导出与路由是两件事

Status: implemented

## Problem

业主现场（2026-10-19）：

> 「养号任务也属于全部任务里面的吧？我执行养号任务，号明明正常却报错，
> 报错什么未在账号池内」

报错原文来自 `crates/ai-gateway-router/src/scheduler/mod.rs`：

```text
该账号不在网关账号池中（可能已禁用、需重新登录或尚未同步）
```

判据是 `auth_by_uid(account_uid)` 返回 `None`。而 `Pool::auth_by_uid` 是**只读
快照**（不排除禁用/冷却），所以 `None` 只有一种可能：**这个账号根本不在池里**。

根因在宿主侧的导出逻辑（`crates/ai-gateway-core/src/modules/gateway.rs`）：

```text
网关的账号池 = 扫描 auth_dir 目录建立的
手动模式下 only = 勾选的 uid 列表
should_export = !needs_relogin(acc) && select_export_uids(...only).is_empty()
             ↑ 未勾选的账号**整份不导出**
```

于是未勾选账号不在目录里 ⇒ 不在池里 ⇒ 养号任务遍历池时找不到它 ⇒ 报错。
而**账号本身完全正常**（能签到、能拉积分、截图里全是 `已签到`），
用户看到这句话只会困惑。

### 这不是新缺陷，是同一个意图只做了一半

`export_accounts_to_dir` 里已有一段注释，讲的是**完全相同的问题**，只是当时修的是「禁用」：

> 「被用户手动禁用的账号要照常导出（与需重登不同）：禁用只表示『别把流量路由给
> 它』，养号任务仍应照跑……此前这里把禁用也一并排除，导致被禁用的账号
> **完全不参与任何养号任务**（实测确认：6 个禁用账号零任务）。现在改为导出时
> 带上 `no_route` 标记，由网关在选号阶段排除。」

那次修好了「禁用」，但「手动模式未勾选」走的是另一条判据（`only` 过滤），
没被一起修 —— **同一个语义缺口，两条不同的代码路径**。

## Decision

把「是否导出」与「是否路由」拆成两个独立判据：

| 判据 | 语义 | 实现 |
|---|---|---|
| **导出** | 这个账号要不要进网关池 | 除 `needs_relogin` 外**一律导出** |
| **路由** | 这个账号要不要参与选号 | 未勾选 / 已禁用 ⇒ 写 `account.no_route` |

改动三处（都在 `crates/ai-gateway-core/src/modules/gateway.rs`）：

1. `build_auth_doc` 新增 `force_no_route: bool` 参数；判据从
   `account_disabled(acc)` 改成 `account_disabled(acc) || force_no_route`。
2. `should_export` 去掉 `only` 过滤，只留 `!needs_relogin(acc)`；
   新增 `is_routed` 单独判 `only`，结果作为 `force_no_route` 传下去。
3. **清理逻辑**同步去掉 `select_export_uids(&all_uids, &only)`。

第 3 处是关键且极易漏：清理逻辑若不改，刚导出的未勾选账号会在**同一个函数里
被立刻删除**。原注释已经警告过这种形态（「导出时不写、清理时又保留」会导致
残留凭证），这次踩的是镜像版本：**导出时写了、清理时又删掉**。

### 为什么选 `no_route` 而不是「另建一个养号专用池」

`no_route` 是**已存在的**语义：`Entry::healthy()` 里
`if self.a.no_route { return false; }` ⇒ 不参与选号；而养号任务遍历的是
`pool_list()`（全池），**不看** `healthy()` ⇒ 照常跑到。

所以这个方案没有引入任何新机制、新字段、新配置。语义上它也与「用户手动禁用」
完全一致 —— 两者都是「别把流量给它，但养号要跑」，合并成一条判据是**正确的抽象**
而不是巧合。

## Alternatives considered

- **在网关侧加一个「养号专用账号目录」，与选号池分开** — 它最强的理由是
  **彻底解耦**：导出目录只放要路由的账号，养号目录放全部账号，两者互不影响，
  以后任何「只想养号不想路由」的需求都能直接加进去，不必再借 `no_route` 的语义。
  否掉的原因是**网关的池是从目录扫描建立的**（`auth::load_dir` 只扫
  `workbuddy*.json`），要支持第二个目录就得改网关的启动参数、配置结构、
  以及「池」这个核心概念 —— 而收益只是把已经存在的 `no_route` 语义拆成两个。
  为一个已经解决的问题引入一层新结构，代价与收益不成比例。

- **只改报错文案**（把「不在账号池中」改成「未加入网关池，请先勾选」） — 它最强的
  理由是**零行为变更**：不动导出逻辑，不会影响选号，风险最低，而用户至少能看懂
  发生了什么。否掉的原因是它把**功能缺失**包装成**提示缺失**：账号明明正常、
  养号任务明明应该跑，却要用户去勾选一个与养号无关的「路由开关」才能用。
  文案能减少困惑，但用户的诉求（跑养号任务）依然没被满足。

- **让养号任务绕过网关，直接读宿主账号库** — 它最强的理由是**从根上分离**：
  养号是宿主的事，本来就不该依赖网关的池；绕过之后「池里有没有它」这个问题
  彻底消失，也不会再有 `no_route` 这种借用的语义。否掉的原因是养号任务的实现
  （签到 / 活跃上报 / 成长任务 / 开学季 / trial）全都在网关 crate 里，用的是
  网关的上游客户端与凭证刷新链路；把它搬回宿主是一次**架构级搬迁**，
  远超本次「修一个报错」的范围。且网关已有的 `no_route` 机制已经能让这件事
  正确工作 —— 缺的只是导出侧那一行判断。

## Consequences

- **收益**：手动模式下未勾选的账号也能跑养号任务，报错消失。
- **收益**：与「禁用」共用同一条判据（`no_route`），不再有两条路径各自演化 ——
  本缺陷的成因正是两条路径分叉。
- **收益**：**手动模式的隔离能力没有被削弱**。实测确认：3 次请求全部用勾选账号的
  token，未勾选账号一次都没被选中。
- **代价**：手动模式下 `auth_dir` 里的凭证文件数变多（全部账号而非勾选的），
  网关启动时要多解析几个文件。可忽略，且这是「养号任务能跑到」的必要前提。
- **代价**：`no_route` 现在承担两种来源（用户禁用 / 未勾选）。它们语义一致，
  但排障时「为什么这个号 no_route」需要看配置模式才能区分。
  **信号**：若将来需要区分（例如界面要显示不同的原因），应加**来源字段**而不是
  拆成两个标记 —— 拆标记会让 `healthy()` 里出现两个并列判据，正是本次要消除的形态。
- **已知上限**：`needs_relogin` 的账号**仍然不导出**（凭证已废，留在池里只会让
  每次请求白跑一轮）。这条边界由 `needs_relogin_accounts_are_still_not_exported`
  钉住，避免把「放宽未勾选」误解成「放宽一切」。

### 实机端到端

隔离实例（独立端口 57961、独立数据目录、独立假上游 57962），两个账号：
一个正常、一个带 `no_route: true`（等价于「手动模式未勾选」）。

| 观察 | 结果 |
|---|---|
| 启动日志 | `rust gateway listening on http://127.0.0.1:57961 (accounts=2)` |
| `/status` | 两个账号**都在池里**；`uid-noroute` 的 `no_route=True`，`uid-routed` 无该字段 |
| 连发 3 次 chat，看假上游收到的 `Authorization` | 全部 `Bearer at-A`（routed 账号），**从未出现 `at-B`** |

第三条是**决定性证据**：它同时证明了「在池里」（否则养号任务跑不到）与
「不参与路由」（否则会看到 `at-B`）—— 这两件事此前是耦合的，现在被正确拆开。

⚠ 实测方法上踩过一次坑（与本次修复无关，但值得记）：`build_auth_doc` 的
`no_route` 只由宿主导出时写入，手工造凭证时**必须自己写 `"no_route": true`**，
否则造出来的「未勾选账号」其实是个正常路由账号，验证会得到假绿。
