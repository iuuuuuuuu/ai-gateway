# Agent Note: 空流风暴阈值对「小池子」永久失效——qoder 只有 2 个账号

Status: implemented

## Problem

业主现场（2026-10-20）：

> 「然后还有我用了一会儿就没办法用了，你也看看咋回事」

日志给出了非常干净的形状。先是 5 次成功：

```text
07:30:53 chat uid=019f1772-… product=qoder model=DeepSeek-Flash: 流结束（已收 58 个有效帧…）
07:31:06 chat uid=01a0c73a-… product=qoder model=DeepSeek-Flash: 流结束（已收 753 个有效帧…）
07:33:33 chat uid=019f1772-… product=qoder model=DeepSeek-Flash: 流结束（已收 21388 个有效帧…）
07:33:57 chat uid=019f1772-… product=qoder model=DeepSeek-Flash: 流结束（已收 427 个有效帧…）
```

然后 `07:34:05` 起，**1 分钟内 23 次**空流，两个账号交替：

```text
07:34:05 chat uid=01a0c73a-… product=qoder: 上游返回空流（无有效数据帧） — 空流不罚号，仅换号（风暴窗口已记）
07:34:05 chat uid=019f1772-… product=qoder: 上游返回空流（无有效数据帧） — 空流不罚号，仅换号（风暴窗口已记）
07:34:05 chat: 轮转耗尽（本请求已试 2 个账号，最后状态 503）
…
07:35:59 chat: 轮转耗尽（本请求已试 2 个账号，最后状态 503）
```

「空流不罚号，仅换号」是刻意的设计（见 `emptystream.rs` 模块文档），问题不在
这里。问题在于**那个本该在此时介入的熔断从来没生效**：

```text
EMPTY_STREAM_THRESHOLD = 3          // 「3 个**不同账号**在 60 秒内空流」
qoder 账号数 = 2                    // ⇒ 上限就是 2，永远达不到 3
```

而原注释把这个副作用当成**有意设计**：

> ★ 副作用是刻意设计：账号总数少于 3 的小池子**永远触发不了**本判定 ——
> 那种池子里换号本来就是把每个号试一遍，没有可省的轮转。

**那句话在「上游整体故障」这个场景下是错的。** 它成立的前提是「账号池健康、
只是个别号有问题」——那时把每个号试一遍确实没有可省的东西。但当**上游整条
通道在故障**时，把每个号都试一遍正是要避免的事：每一次尝试都是一次真实的
上游请求，只会加深上游对该账号/该出口的风控，而用户拿到的是 23 次 503。

这正是本模块开头自己描述的那个放大循环：

> 网关的既有逻辑是「空流 ⇒ 冷却换号」，于是… 30 行「chat uid=… 上游返回空流」

## Decision

阈值从**固定常量**改成**按通道账号总数夹小**：

```text
effective_threshold(accounts) =
    accounts == 0                    => 2
    accounts <= EMPTY_STREAM_THRESHOLD => clamp(accounts, 2, 3)
    accounts >  EMPTY_STREAM_THRESHOLD => 3   （不变）
```

三条边界：

1. **只夹小、绝不放大**：大池子（WorkBuddy 19+ 个账号）行为**完全不变**，仍是 3。
2. **下界 2**：阈值 1 会让**单个**账号的一次偶发空流立刻熔断整条通道 —— 那正是
   本模块开头警告的「单号问题被误判成上游整体故障」。两个**不同**账号在同一
   窗口内都空流，才排除了「单个账号自己的问题」。
3. **`accounts == 0` 返回 2**：池子里没有该通道的账号时根本选不到号，轮转会在
   别处失败，不该由这里给出「上游故障」这个错误结论。

### 账号数从哪来：新增 `Pool::channel_account_count`

```text
Pool::channel_account_count(product, region) -> usize
```

★ **不过滤健康度**。熔断要回答的是「这个通道还有没有别的号可换」，已冷却的号
同样换不到。只数健康号会让阈值随冷却状态漂移 —— 同一场故障在不同时刻得出
不同结论，而这种漂移在日志里完全看不出来。

调用点在 `forward.rs` 的空流熔断段，**发请求之前**取一次：

```text
let accounts = pool.channel_account_count(acct.product_of(), acct.region().as_str());
let (burst, distinct) = ctx.empty_stream.blocked(product, region, accounts);
```

`blocked()` 的签名因此多了一个参数。这比「让 `EmptyStreamWindow` 自己持有池子
引用」好：`EmptyStreamWindow` 是个纯状态机（带可注入时钟、503 行里一半是测试），
把它和账号池绑在一起会让它无法单测。

### 日志要能自证阈值

熔断命中时的日志补上阈值与该通道账号数：

```text
chat: 空流风暴熔断中（最近 60 秒内 2 个不同账号空流，阈值 2，该通道 2 个账号），不发请求
```

否则下次看到「2 个账号就熔断了」会以为阈值被谁改小了。**判据必须能自证**。

## Alternatives considered

- **把常量直接改成 2** — 它最强的理由是**一行改完**：不需要新参数、不需要
  `Pool` 新方法、`blocked()` 签名不变，所有既有测试一个字都不用动。否掉的原因是
  它会**削弱大池子**：WorkBuddy 有 19 个账号，阈值降到 2 意味着「任意两个账号
  空流就熔断整条通道」—— 而现场记录过 6 波并发重试，两波偶发凑巧撞上完全可能。
  那会把「偶发」误判成「上游整体故障」，把本来能用的通道停掉。阈值必须与池子
  大小挂钩，不能一刀切。

- **在 `EmptyStreamWindow` 里存一份「通道账号数」注册表** — 它最强的理由是
  **调用点最干净**：`blocked(product, region)` 签名不变，由池子加载时调一次
  `set_accounts(product, region, n)` 注册。否掉的原因是**状态会漂移**：账号是
  热加载的（`watch_auth_dir` 每 5s 扫一次），注册表要跟着每次变动更新，漏一次
  就永久用旧值。而「每次判定现取」的成本只是一次 `Mutex` 锁 + 一次线性计数
  （几十个元素），在请求路径上完全可忽略。**能现算的就别存副本。**

- **让 `blocked()` 直接接收 `&Pool`** — 它最强的理由是**类型上不可能传错**：
  调用方拿不到「传哪个数」的选择权。否掉的原因是把 `EmptyStreamWindow` 从纯
  状态机变成依赖 `Pool` 的组件：它的 13 条单测全靠「注入假时钟 + 手工 note」
  驱动，一旦要构造 `Pool`，测试就从「测判定逻辑」变成「测池子装配」。
  传一个 `usize` 是最小的耦合面。

- **对 qoder 单独设一个更低的常量** — 它最强的理由是**意图最直白**：qoder 就是
  2 个号，写死 `QODER_EMPTY_STREAM_THRESHOLD = 2` 一眼就懂，也不必给 `Pool`
  加方法。否掉的原因是**把「账号数」这个事实抄成了第二份**：将来 qoder 加到
  5 个号时，这个常量不会跟着变，于是「5 个号却按 2 个号熔断」——同一类缺陷
  换个形态复发。阈值要由**当下的事实**算出来，不能抄快照。

## Consequences

- **收益**：qoder 通道上的风暴熔断从**永久失效**变成真正生效。现场那种
  「1 分钟 23 次空流、每次轮转耗尽」的循环，在**第 2 个不同账号空流**时就会
  被拦下，后续请求直接返回带说明的 503（`empty_stream_burst_message`），
  而不是继续打上游。
- **收益**：WorkBuddy 的行为**零变化**（19 ≥ 3 ⇒ 阈值仍是 3），
  所有既有大池子测试的断言原样保留（只是多传一个 `BIG_POOL = 19`）。
- **收益**：阈值与账号数挂钩后，新增单账号产品（未来的 ZCode 小池子等）
  自动获得正确的熔断行为，不需要再为新池子调常量。
- **代价**：`blocked()` 的签名多一个 `usize` 参数，`forward.rs` 的调用点要多锁
  一次池子。后者在同一段代码里已经有若干次池子访问，成本可忽略。
- **代价**：`effective_threshold` 的 `accounts == 0 => 2` 是一个**无法从现场
  观察到的分支**（池子里没有该通道账号时选号在别处就失败了）。它是防御性写法，
  只有单测覆盖 —— 已在 `threshold_is_clamped_not_raised` 里钉住。
- **已知上限**：熔断生效只解决「不要继续打上游」，**不解决上游为什么空流**。
  本次现场的两个可能原因（上游限流 / 请求形态不对）里，后者由
  [Qoder 请求身份与代理](2026-10-20-qoder-request-identity-and-proxy-not-wired.md)
  处理了一部分（国际版直连慢会表现为超时型空流），但**上游限流本身没有证据**。
  **信号**：若熔断已生效而 qoder 仍频繁进入熔断态，说明问题在上游侧
  （额度/风控），该做的是查账号额度与上游公告，不是继续调这个阈值。
- **未证**：现场 23 次空流的**直接原因**没有被证实。本次修复的是「网关对空流的
  反应方式」（从无限换号变成熔断），不是「空流的成因」。这两件事必须分开说 ——
  把前者说成后者就是假交付。

## Verification

单测（`cargo test -p ai-gateway-router --lib emptystream`，13 passed）：

- `small_pool_reaches_verdict` —— 2 个账号的通道上，第 2 个不同账号空流即判定。
  这条直接复现现场形状。
- `single_account_channel_never_self_trips` —— 单账号反复空流 10 次**仍不**判定
  （下界 2 的意义）。
- `threshold_is_clamped_not_raised` —— `0/1/2/3/19/1000` 六个输入的边界表，
  断言只夹小不放大。

**故障注入（已做）**：把 `effective_threshold` 还原成 `EMPTY_STREAM_THRESHOLD`
（固定 3），`small_pool_reaches_verdict` 与 `threshold_is_clamped_not_raised`
立刻变红（`left: 3, right: 2`）。恢复后全绿。

**未覆盖**：`Pool::channel_account_count` 本身没有单测 —— 它是三行过滤器，
且已在 `forward.rs` 的集成路径上被调用。这是已知的小缺口。

## ⚠ 后续修正（2026-10-20，同一现场）

本篇的阈值夹小**是必要但不充分的**：qoder 的两个账号分属 `cn` / `intl`，
而 `qoder:模型名` 的轮转是整产品。窗口却按**账号区域**分桶 ⇒ 两个账号各进一个
「只有 1 个账号」的桶，阈值下界 2 永远凑不满 —— 现场 08:36 的 8 次空流里
熔断仍然一次都没触发。

真正的修法是让分桶与轮转范围一致，见
[空流窗口按账号区域分桶](2026-10-20-empty-stream-window-key-split-by-account-region.md)。
本篇的 `effective_threshold` 结论不变，但**不能**再单独宣称「小池子自动获得
正确熔断」—— 前提是同一桶里确实能看到多个账号。
