# Agent Note: 被封账号的 11140 被误判成 3012，熔断整个区域

Status: implemented

## Problem

原 `docs/DECISIONS.md` D20（从 DECISIONS.md 迁移）。

业主现场（第三轮，装上 D18/D19 的包之后）：

> 「要的，不然我现在发送就直接死了」「这个错误 导致我现在根本用不了」
> 附 503 `unusual_activity`，倒计时 66 秒。

先确认 D19 已上线：宿主 `D:\APP\AI Gateway\ai-gateway.exe` 时间 08:35、
`_up_/assets/wb-device-token/turing-sdk-shim.cjs` 已就位；网关侧「设备 token 获取失败」
日志**降为 0 条**（修复前每次请求都失败），且国际版账号 `<uuid>` 在 08:54 流式成功。
⇒ 设备 token 修复**已生效**。

真根因：**一个被封账号把整个国际版区域熔断了 90 秒**。逐账号直连上游实测
（12 个国际版账号，带真实 device token）：

| 状态 | 数量 | 账号 |
|---|---|---|
| ✅ 成功（HTTP 200，流式） | **4** | 4 个国际版账号（占位名 `acct-1`…`acct-4`） |
| ⏳ 频率限制 6004（正常，非封禁） | 7 | 其余 |
| ❌ **403 / 11140** | **1** | **`<uuid-A>`** |

即 **11 个好号 + 1 个坏号**。而那一个坏号让**整个 (workbuddy, intl) 被熔断**。

不修的话，只要账号池里存在一个已被上游封禁的号，该区域每轮都会被重新选中并熔断，
11 个好号一起被挡 —— 表现为「发送就直接死了」，且**无法自愈**（坏号永不冷却）。

## Decision

### 缺陷链条（每一环都有实测证据）

上游对**被限制的账号**回的 403 body **逐字**是：

```json
{"code":11140,"msg":"request illegal",
 "displayMsg":{"en":"Your account has been restricted due to unusual activity",
               "zh":"账号存在异常行为，已被限制使用"},
 "displayTips":{"en":"We detected unusual activity on this account. ..."},
 "actions":["EDIT_INPUT","SUBMIT_FEEDBACK"]}
```

⚠ 注意 `displayMsg.en` 里含 **`unusual activity`** —— 而 `unusual.rs` 的
`is_unusual_activity()` 判据之一是**全文小写子串**匹配该短语：

```text
上游 403/11140（账号被封，文案含 unusual activity）
  ⇒ is_unusual_activity() 命中 ⇒ 走 3012 分支
  ⇒ 3012 分支**刻意不罚账号** ⇒ 坏号永不冷却 ⇒ 每轮换号重新选中
  ⇒ 且**熔断整个 (产品, 区域)** 90 秒 ⇒ 同区 11 个好号一起被挡
```

**两者的处置完全相反**：

| | 11140 账号被封 | 3012 请求级风控 |
|---|---|---|
| 归属 | **账号侧**（`classify.rs` 第 12 条） | 请求 / 出口侧 |
| 处置 | 软冷却该号 + 换号 | 熔断区域 + 不罚账号 |
| 换号有用吗 | **有用**（换号即好） | 无用（换号加重风控） |

### 修法

把判定抽成纯函数 `forward.rs::should_trip_unusual_breaker(kind, status, body)`：
**`ErrKind::AccountUnusable` 直接返回 false**，其余照旧交给 `is_unusual_activity`。
命中 11140 的响应于是不再走 3012 分支，而是落到通用 `apply_error_policy`
→ 账号级**软冷却** → `continue` 换号（该路径已存在，见 `forward.rs` 的
`ErrKind::AccountUnusable` 臂）。

### ⚠ 第一版修复是**假绿门禁**，已纠正（本轮教训）

第一版把条件内联在轮转循环里（`if !is_account_unusable && is_unusual_activity(...)`），
并配了 3 条测试。**但故障注入显示：把条件改回缺陷版本，全量单测仍然全绿** ——
因为那 3 条测的是 `classify` 与 `unusual` 两个**判据各自**的行为，
**没有任何一条钉住 `forward.rs` 里的那个组合条件**。测试够不着被改的代码。

纠正方式：把判定**抽成纯函数**，由 `unusual_breaker_excludes_banned_account`
直接钉住。**再次注入确认变红**（panicked，文案即现场描述），撤销后复绿。

★ 这条教训的一般形式：门禁「绿」不代表它守着被改的那行。判断方法是**注入**
——把缺陷改回去看它是否变红；内联在循环里的条件几乎总是不被钉住的，
因为能钉住它的只有那个组合本身，而组合没有名字。

## Alternatives considered

- **保留内联条件，只补几条测试** — 它最强的理由是改动最小、且不引入新函数：
  逻辑就在轮转循环里，补测试直接测它即可，不必为此重构 `forward.rs` 的结构。
  否掉的原因是被实测否掉的：第一版正是这么做的，而注入缺陷版本后全量单测**仍然全绿**
  —— 那 3 条测的是 `classify` 与 `unusual` 各自的判据，够不着组合条件。
  没有名字的组合无法被单独断言，所以必须先抽成纯函数。

- **在 `is_unusual_activity()` 里直接排除 11140 文案** — 它最强的理由是把修正放在
  判据的源头：误判发生在「文案匹配」这一步，就地改匹配规则最直接，所有调用方一次修好。
  否掉的原因是它会改变 `is_unusual_activity` 的语义边界 —— 这个函数回答的是
  「这段报文看起来像不像 unusual activity」，而 11140 的文案**确实**含该短语；
  真正要区分的是「命中之后该怎么处置」，那是调用方的决定。改判据会让
  `banned_account_body_does_match_the_3012_markers` 这条记录事实的测试失去意义。

- **让 3012 分支也罚账号（统一处置，不再分流）** — 它最强的理由是消除两条相反的
  处置路径：既然都会导致请求失败，就一律软冷却换号，代码路径单一、不用维护
  「谁罚谁不罚」的规则。否掉的原因是 3012 是**请求 / 出口侧**的风控，
  换号会**加重**风控；对它罚账号等于把一次请求级风控升级成账号级损失，
  与 11140 的正确处置正好相反。

- **对 11140 直接熔断区域（与 3012 同处置）** — 它最强的理由是保守：
  既然上游说「request illegal」，整片区域可能都有问题，停下来最安全。
  否掉的原因是实测数据否定了这个前提：12 个账号里 11 个是好的
  （4 个 200 流式 + 7 个 6004 频率限制），坏的只有 1 个 —— 熔断区域会拿 1 个坏号
  去停掉 11 个好号。

## Consequences

- **收益**：一个被封账号不再拖累同区其它 11 个账号 —— 熔断的归属与上游的错误归属
  对齐了（账号侧的错误按账号处置，区域侧的错误按区域处置）。
- **收益**：坏号走 `apply_error_policy` 的账号级软冷却并 `continue` 换号，
  这是既有路径，不新增状态机；「换号即好」这条语义被恢复。
- **收益**：判定有了名字（`should_trip_unusual_breaker`），门禁可以直接钉住它 ——
  这是本轮真正的产出，比修好这一条错误更重要。
- **代价与已知上限**：**`<uuid-A>` 这个账号本身是被上游封禁的**
  （`displayMsg`：「账号存在异常行为，已被限制使用」，`actions` 里给了
  `SUBMIT_FEEDBACK` 申诉入口）。本次修复让它**不再拖累其它 11 个账号**，
  但它自己仍然不可用 —— 只能去官方客户端提交反馈 / 申诉。
  **已封禁的账号补 device token 也救不回来**（见 D19）。
- **代价与已知上限**：判定依赖 `ErrKind::AccountUnusable` 的分类正确性。
  若 `classify.rs` 把某个响应归错类，这里的排除就会失效 —— 而表现是「又熔断整个区域」，
  不会报错。
- **信号（翻案条件）**：若上游将来把 `unusual activity` 从 11140 的文案里去掉，
  则 `banned_account_body_does_match_the_3012_markers` 会失败 —— 那说明误判不再可能，
  届时可简化 `should_trip_unusual_breaker` 的判断，但**不要**直接删掉那组测试。

**观察判据**：修复后网关日志里该账号的归因会从「3012 unusual activity」
变成「11140（账号被限制）」—— 这条差异可直接用来确认修复生效。
