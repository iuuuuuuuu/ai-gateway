# Agent Note: 连败降权——「不知道原因」的失败攒够次数才让账号出池

Status: implemented

## Problem

网关里有两类失败**没有任何惩罚**，账号会被无限重选：

| 失败类型 | 旧行为 | 后果 |
|---|---|---|
| `ErrKind::Client`（未知 4xx 的兜底分类） | `apply_error_policy` 的 `_ => {}`，只换号不罚 | 持续返回未知 4xx 的账号**永不冷却**，每轮都被重新选中 |
| 传输层失败（超时 / 连接被拒 / DNS） | 只记 `last_transport_err` 后 `continue` | 持续连不上的账号**永不冷却**，每轮都被重新选中 |

这两处的注释都写着「只换号不罚（防雪崩）」——那个理由本身是对的：单次未知失败
不能罚号，否则一次网络抖动就把健康账号冷却掉。但它把手段用错了：
**「不罚单次」被实现成了「永不惩罚」**，于是一个真正坏掉的账号会在每轮请求里
被重新挑中、重新失败，用户看到的是「每次都要等一轮超时」。

`Client` 是 `classify()` 的兜底分类（`classify(400, "")` 的既有测试就断言这一点），
所以它涵盖所有「4xx 但不是已登记业务码」的形态——范围很宽，长期不罚代价明显。

## Decision

新增**连败降权**：`Client` 与传输层失败各喂一个连败计数器，
连续达到阈值（默认 5 次）后把账号**临时**移出选号池（默认 10 分钟）。

三条语义边界：

1. **只喂「不知道原因」的失败。** 带权威分类的错误（`429` / `402` / `5xx` /
   `12153` / `11140` / `11102` / WAF）**不喂** —— 它们各自已有冷却 / 熔断 / 禁用 /
   负缓存，再喂连败就是**重复计罚**。这是本次改动最容易写错的地方。
2. **单次失败不罚。** 计数只在达阈时生效；1~4 次失败不改变任何行为。
3. **降权期内再达阈不延长、不翻倍。** 计数清零后重新累计，但 `degrade_until`
   一毫秒都不动 —— 防用户重试把降权越堆越厚（与 `CooldownSoftRate` 的兜底探测同哲学）。

### 为什么是「不同入口计数」而不是「按错误次数」

`Client` 与传输层是两个独立入口，各自喂同一个计数器。这样「同一个坏账号反复失败」
与「多个账号各失败一次」都能正确累计——而 WAF IP 级判定（`wafip.rs`）刻意用的是
**不同账号数**，因为那里要证明「多个独立凭证一起失败 ⇒ 问题在出口 IP」。
两者判据不同是**有意的**：降权针对**单个账号**的健康度，IP 级针对**共用出口**。

### 判定落在 `healthy()`

`Entry::healthy()` 是**全部选号路径的唯一闸门**（模块文档原话：「所有选号路径
（主路径、兜底、按 uid、探测）都经由它，不存在第二条需要单独维护的检查」）。
降权作为**第四条并列或门**加进去：

```text
healthy = !disabled && !no_route && !daily_guard && !until && !breaker_until && !degrade_until
```

「与既有冷却并存取更长者」由或门天然保证，**不做任何 min/max 叠加计算**。

⚠ 但 `pick_earliest_expiry`（全冷却兜底）**不调** `healthy()`，必须**显式**再写一遍
降权排除 —— 这是本仓库踩过两次的缺陷类型（`no_route` 与 `daily_guard` 都栽过：
主路径排除了、兜底路径漏了，表现为「用户关掉的账号仍被选中」）。

### 持久化

- `consecutive_fails` **恒恢复**（`max(0)`）：半开进度，重启不重学。
- `degrade_until` **仅未过期时**落盘 / 恢复：已过期的截止在语义上等价于「没降权」，
  写进文件只会让下次读盘多一条无效状态（与 `breaker_until` 同款惰性过滤）。

### 配置

三个键（`pool.degrade_*`），沿用 `breaker_*` 家族的风格：

| 键 | 默认 | 语义 |
|---|---|---|
| `degrade_threshold` | 5 | 达多少次触发；**0 = 关闭整个机制** |
| `degrade_cooldown_secs` | 600 | 降权时长（唯一来源） |
| `degrade_cooldown_max_secs` | 600 | **只解析、不接逻辑**，见下 |

★ `degrade_threshold` 的 `0` **就是「关闭」**，与 `breaker_threshold` 的
「非正即不覆盖」**不同**。故 `set_degrade` 对 `threshold >= 0` 全部接受，
接线处**不做任何 `max(1, …)` 式保护** —— 那会把用户的关闭动作变成静默开启。

★ `degrade_cooldown_max_secs` **加字段但不接逻辑**：当前设计「不延长不翻倍」
⇒ `min(d, max)` 恒等于 `d`，读它没有意义。保留它的三条理由：① 宿主若写出该键，
网关没有字段就是**静默不生效的键**（`pool.multi_product` 同型先例）；
② 它是「不许加长」这条设计约束的**显式落点**，将来若改成「重犯加长」第一个动它；
③ 代价仅启动期一次解析。接线处**刻意不往下传** —— 传一个没人读的值会让后人
误以为上限真的生效了。

## Alternatives considered

- **让 `Client` 直接走 `note_error`（熔断）** — 它最强的理由是**零新增机制**：
  熔断已经有指数退避、有持久化、有 `/status` 透出，复用它不需要新字段、新配置、
  新状态机，改动面小一个数量级。否掉的原因是**语义不对**：熔断的语义是
  「上游在坏」，退避时间按 `retry_count` 逐次翻倍（30 分钟起）；而 `Client` 是
  「不知道谁坏了」——可能只是这个账号的凭证状态不对，也可能只是这次请求撞上了
  上游的一次性校验。用 30 分钟起的翻倍退避去罚一个「不知道原因」的失败，
  惩罚过重且会翻倍失控。降权固定 10 分钟、不翻倍，才是这个不确定性该配的力度。

- **不设连败阈值，`Client` 一次就罚** — 它最强的理由是**简单**：不需要计数器、
  不需要阈值配置、行为一眼可预测。否掉的原因是它正是旧注释担心的那个雪崩形态：
  `Client` 涵盖所有未登记 4xx，一次上游抽风就会把健康账号冷却 10 分钟，
  而用户完全不知道发生了什么。单次未知失败的信息量**不足以**判定账号坏了。

- **把 `Client` 从兜底分类里拆细，让每种 4xx 都有自己的惩罚** — 它最强的理由是
  **治本**：连败降权本质是「分类不够细」的兜底，真正该做的是让 `classify()`
  多认出几种形态（像 11115 / 11133 / 11140 那样各有专门分支），那就不需要兜底了。
  否掉的原因是**信息不足**：兜底分类之所以是兜底，就是因为上游会返回我们没见过的
  形态；拆得再细，兜底里永远还剩东西。而且拆细需要真实样本，现在没有。
  ⇒ 降权是「不知道原因时」的正确姿态，与「继续拆细」不冲突，两者可并存。

## Consequences

- **收益**：持续失败的账号不再被无限重选，用户不再每次都要等一轮超时。
- **收益**：与既有惩罚**不叠加**（只喂无权威分类的两类），不会出现「一个错误罚两次」。
- **收益**：`/status` 能看出降权态（`cool_kind="degrade"` + `degrade_until` + reason），
  排障时不用猜「为什么这个号没被选中」。
- **代价**：多一个状态机、两个持久化字段、三个配置键。**信号**：若 `/status` 出现
  `cool_kind="degrade"` 而用户认为该账号是健康的，说明阈值太低或某些本该有专门分类的
  错误落进了 `Client` —— 该去补 `classify()` 的分支，而不是调高阈值。
- **代价**：`degrade_cooldown_max_secs` 是个**无人读取的字段**。这是有意的（见上），
  但它确实会被误读成「上限生效中」。已在该字段文档与接线处两处写明。
- **已知上限**：降权只影响**选号**，不影响养号任务（签到 / 上报 / 成长）——
  那些走 `probe_uids` / `all_uids`，**刻意不排除**降权号。理由：探测是只读链路，
  成功一次就是最强的反证，让它跑反而能更快把账号救回来。

### 实机端到端（隔离实例，真实 HTTP）

隔离方式：独立 target 目录构建、产物改名 `degrade-probe.exe`、独立数据目录
（`AI_GATEWAY_HOME` 之外的独立 `auth_dir` / `state_file`）、独立端口 `57931`、
假上游 `57932`~`57936`。**业主的 `:7864` 与 `:3080` 全程未触碰**（PID 始终 17360 / 48144）。

★ 关键发现：上游基址**不是配置项，是环境变量** `WB2A_CHAT_BASE_CN`
（`bin/gateway.rs:474`）。第一轮实测把 `upstream.chat_base_cn` 写进 JSON 配置，
结果请求全打到真实的 `copilot.tencent.com`（返回 APISIX 的 401 HTML）——
**假上游只收到一次探活**。这是实测方法错了，不是代码缺陷。

真实假上游（`fake-upstream-switch.cjs`，可动态切 fail/ok）+ 真实 HTTP 请求，六项：

| # | 做了什么 | 观察到什么 | 判定 |
|---|---|---|---|
| 1 | 发 1 次 Client 失败 | `fails=1`，`degrade_until` 空，`cooling=false` | ✅ 单次不误伤 |
| 2 | 发第 2 次 | `fails=2`，仍未降权 | ✅ 连败正常累计 |
| 3 | 发第 3 次（threshold=3） | `fails=0`，`degrade_until=23:32:43`，`cool_kind="degrade"`，reason「连续未知失败降权（达阈 3 次）」 | ✅ 达阈触发 |
| 4 | 降权期内再请求 | 假上游命中数 **1 → 1 不变** | ✅ 账号已被排除出选号池 |
| 5 | 等 8 秒（cooldown=6s） | `cooling=false`，`degrade_until` 清空；再请求命中数 5 → 6 | ✅ 到期自动回池 |
| 6 | 失败2 → **成功1次** → 再失败2 | `fails` 走 `2 → 0 → 2`，始终未达阈 | ✅ 成功清零（决定性用例） |
| 7 | 传输层失败（上游指向 `127.0.0.1:1`）连打 3 次 | 第 3 次 `cooling=true`、`cool_kind="degrade"` | ✅ 第二个喂入口生效 |

★ 第 6 项是**最关键**的一条：它证明「成功清零」发生在**真实请求路径**上，而不只是
单测里调了 `note_success`。做法是同一个网关进程内切换假上游的 fail/ok 模式
（`mode.txt`），不重启、不重置状态。

★ 实测中确认了两个**会误导判据**的细节（写下来免得后人重踩）：

1. **`consecutive_fails` 达阈后是 0，不是 5** —— `note_failures` 达阈即清零供下轮累计。
   所以**不能用它判断是否降权**，要看 `degrade_until`。
2. **`Status.cooling` 是「此刻不接客」的投影，不是惩罚本身** —— `pool.rs` 刻意把降权
   也算进 `cooling`（否则界面会出现「0 冷却但 healthy 少一个」，数字对不上）。
   判断「这是不是降权」要看 `cool_kind == "degrade"`。

★ 假上游返回普通 JSON（非 SSE）时，网关会报「上游返回空流」并判失败 —— 这是**正确**的
保护（200 + 空流是真实存在的失败形态，见 `emptystream.rs`），不是缺陷。要做成功路径
的实测，假上游必须返回 SSE 数据帧。
