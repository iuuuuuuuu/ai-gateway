# Agent Note: 数据目录回到 .wb-switch，但环境变量名刻意不改

Status: implemented

## Problem

原 `docs/DECISIONS.md` D04（从 DECISIONS.md 迁移）。1.0.0 更名时把数据目录换成了
`~/.ai-gateway` 并做一次性「复制式迁移」。但 2026-09-16 起本仓库与老仓库
（`workbuddy-switch-gateway`，0.8.x 线）**并行维护**、两版会同时装在一台机器上，
于是迁移暴露出一个真实的数据缺陷：

> 迁移的幂等标记 `.migrated-from-wb-switch` 让迁移**只跑一次**，此后 `.ai-gateway`
> 就成了迁移那一刻的快照。用户在任一版本里新增的账号都不会出现在另一个版本里 ——
> 而从用户视角这是**同一个应用的两代**，理当共用同一份账号库。

不处理这个缺陷，两版并行期间用户会看到「同一个应用，装了两个版本，账号却互不相见」，
且新增账号越多、分叉越深。同时还要决定：目录既然改回 `.wb-switch`，环境变量名
跟不跟着改。

## Decision

### 数据目录是 `%USERPROFILE%\.wb-switch`

数据目录是 `%USERPROFILE%\.wb-switch`；`.ai-gateway` **不再被写入**，仅作为一次性迁移来源。

### 环境变量仍叫 `AI_GATEWAY_HOME`

环境变量**仍叫 `AI_GATEWAY_HOME`**，不随目录改名。

### 为什么环境变量名不改

它是**新版本才引入的**，改名只涉及源码；改了反而会让既有的隔离脚本失效。
⇒ 改名收益为零、代价是破坏已存在的自动化。

### 迁移语义

- **复制式**：旧目录原样保留，可随时回退。
- **设了 `AI_GATEWAY_HOME` 时不迁移** —— 那说明用户在刻意隔离（开发/测试实例），
  把真实用户数据搬进去反而会污染隔离环境。

## Alternatives considered

- **继续用 `.ai-gateway` 并靠「双向同步」维持两版一致** —— 它最强的理由是**不必动
  已发布的路径**：用户的 `.ai-gateway` 已经在那儿，改回去意味着再迁一次；而双向同步
  表面上能让两版各写各的、又能看到对方的账号。否掉的原因是那要写一个**永不收敛的同步器**
  —— 两版都在写、没有单一真源，冲突无法自动裁决。

- **把环境变量一并改名** —— 它最强的理由是**命名一致**：目录叫 `.wb-switch`、
  变量还叫 `AI_GATEWAY_HOME`，读代码的人会以为变量指向旧目录；统一命名能消除这个误解，
  且变量是新版本才引入的、改名只涉及源码，改动量很小。否掉的原因是它**纯破坏性变更**：
  改名会让既有的隔离脚本失效，收益为零、代价是破坏已存在的自动化。

## Consequences

- **收益**：两版（本仓库与 0.8.x 老仓库）共用同一份账号库，不再出现「迁移那一刻的快照」
  导致的分叉；`.ai-gateway` 只作为一次性迁移来源，不再被写入；复制式迁移保留旧目录，
  随时可回退；设了 `AI_GATEWAY_HOME` 时不迁移，隔离环境不被真实数据污染；
  环境变量名不变，既有隔离脚本继续有效。
- **代价与已知上限**：目录名与变量名不一致（`.wb-switch` vs `AI_GATEWAY_HOME`），
  读代码的人需要知道这是**刻意的**；迁移分支必须与老仓库并行期共存。**什么信号发生时
  必须重访该决定**：老仓库（0.8.x 线）停止维护、且不再有用户在两版之间来回切换时，
  可以删掉迁移分支；环境变量名**仍不建议改**。

## Verification

- 迁移幂等标记：`.migrated-from-wb-switch`（决定「迁移只跑一次」的那个标记，
  也是上面那个数据缺陷的成因）。
- 环境变量消费点：`crates/ai-gateway-core/src/modules/config.rs` 认 `AI_GATEWAY_HOME`
  （用于开发/测试隔离）；设了它时迁移分支不执行。
- 目录形态：`%USERPROFILE%\.wb-switch`（现行）与 `%USERPROFILE%\.ai-gateway`
  （仅迁移来源，不再写入）。
