# Agent Note: 并发上限每账号 3 + 换号重试（Go 的排队语义未随重写保留，未决）

Status: implemented

## Problem

原 `docs/DECISIONS.md` D10（从 DECISIONS.md 迁移）。症状是「同一个模型、同一个网关 —— 用 `curl` 发**每次都成功**，但客户端**每次都失败**（`503 no_healthy_account`）」。根因是客户端的 LLM 层会**并发重试**：DSH 用的 `@earendil-works/pi-ai` 带 `retryProviderRequest`，默认**重试 5 次**，**每个重试是独立的并发请求**。而 `max_in_flight` 是**每账号**上限，qoder / zcode **各只有 1 个账号** ⇒ 该产品的总并发 = 这个上限。

不设这个上限，或把它设成「刚好等于上游能力」，都会在客户端一重试时直接越界 —— 表现不是慢，而是**成片的 503**；而 `curl` 单发永远看不出问题，排查时极易被误判成「网关坏了」或「上游故障」。

## Decision

### 每账号 3，满额返回 false 而不是等待

`pool.max_in_flight = 3`（**每账号**上限，三个产品统一）。名额满时 `Pool::acquire()` **返回 false**，调用方**换号重试**。

### 这个值的历史：`3 → 32 → 8 → 16 → 3`（每次都是实测驱动）

- `32`：**恰好压在 qoder 上游的并发天花板（≈30）上** ⇒ 一重试就越界。**教训：上限不能设成「刚好等于上游能力」** —— 网关自己的巡检/保活也占在途名额，必须留余量。
- 回到 `3`：因为**每账号** 3 在 19 个 WorkBuddy 账号上就是总并发 57，够用。

### ★ 未决的行为漂移（必须写下来）

Go 版当年**敢用 3** 的前提是**名额满时排队等待**（`server.Config.InFlightWait` 默认 3000ms / `pool.AcquireWait`）。Rust 版**没有实现排队**：`in_flight_full()` + `acquire()` 满额直接返回 false，唯一调用点 `forward.rs` 是**换号重试**。⇒ 对**单账号产品**（qoder / zcode）「换号」无处可换，**正是「并发重试成片 503」的成因形状**。而 `crates/ai-gateway-core/src/modules/gateway.rs` 里那段「为什么现在敢用 3」的说明是 **Go 时代遗留**（引用的 `InFlightWait` / `AcquireWait` 在 Rust 侧只存在于注释里，**没有任何实现**）。

### ⚠ 未决事项：需要 Owner 定夺

⚠ 这条**需要 Owner 定夺**：保留换号，还是补回排队。**在定夺之前不要凭感觉改这个 3。**

即「每账号 3」这个数值本身**仍在执行**，但它赖以成立的前提（排队）已经不在 Rust 侧 —— 这是**待定夺的未决项**，不是已定案的取舍。读到这篇的人不应把它当成「3 是对的」的结论。

## Alternatives considered

- **把上限开大** — 它最强的理由是**当场就能消除 503**：名额不够，加名额是最直接的解法，不需要动 `forward.rs` 的调用路径，也不需要碰 Go 时代遗留的注释。否掉的原因是治标 —— 真正的问题是「满了之后怎么办」，不是「上限多少」；上限越大，越容易像 `32` 那次一样直接压到上游天花板上。

- **把上限设成刚好等于上游能力** — 它最强的理由是**最大化利用率**：既然 qoder 上游大约能扛 30 个并发，把上限设到 30 附近就能把通道吃满，不浪费配额，也不用解释为什么留空。否掉的原因是这正是 `32` 那条实测教训：**上限不能设成「刚好等于上游能力」** —— 网关自己的巡检/保活也占在途名额，没有余量时「一重试就越界」。

## Consequences

- **收益**：`max_in_flight` 有了明确的取值依据（实测驱动的 `3 → 32 → 8 → 16 → 3`），多账号产品靠「每账号 3」拿到足够的总并发（19 个 WorkBuddy 账号 = 57）；满额时不会静默排队拖长请求，而是立刻换号，把压力分散到别的账号上。
- **代价与已知上限**：对**单账号产品**（qoder / zcode）「换号」在定义上无处可换，满额即失败 —— 这一点**未证**的只有「客户端并发重试是否还会再次成片 503」。原文的翻案条件有两条，任一成立就该动手：① **再次出现「并发重试成片 503」，且已排除上游故障** ⇒ 把「排队等待」补回 Rust 侧，而不是继续调这个数字；② 单账号产品（qoder / zcode）开始承载真实并发流量时 —— 那时「换号」这条路在定义上就是死的。**这两条信号一旦出现，就是必须重访该决定的时刻**；此外任何「凭感觉改这个 3」的行为都不算重访。

## Verification

- 值历史的每一档都是**实测驱动**的（`3 → 32 → 8 → 16 → 3`），不是估算：`32` 那一档的实测结论是「恰好压在 qoder 上游的并发天花板（≈30）上 ⇒ 一重试就越界」。
- 回到 `3` 的可算依据：**每账号 3** × 19 个 WorkBuddy 账号 = 总并发 **57**，够用。
- 现状口径（Rust 侧）：`in_flight_full()` + `acquire()` 满额直接返回 false，唯一调用点是 `forward.rs` 的**换号重试**；`InFlightWait` / `AcquireWait` 在整个 Rust 侧**只存在于 `gateway.rs` 的注释里，没有任何实现**。
