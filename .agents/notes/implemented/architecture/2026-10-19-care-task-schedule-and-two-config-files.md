# Agent Note: 养号任务的排程机制——两个配置文件、启动补跑、以及「自动跑 ≠ 手动能跑」

Status: implemented

## Problem

业主提问（2026-10-19，紧接「八个入口全报不在账号池内」那个修复之后）：

> 「你看一下养号任务会不会主动触发」

这个问题看起来简单，实际有三个陷阱，每个都足以让人得出**错误结论**。本文记录核实过的机制，
避免下次（无论是我还是后来者）在验证「自动触发是否工作」时再次走错。

### 陷阱一：有两个配置文件，读的不是你改的那一个

同一台机器、同一时间，两个都存在、都叫「配置」：

| 文件 | 谁读 | 结构 | 谁写 |
|---|---|---|---|
| `~/.wb-switch/gateway/gateway_config.json` | **你**（界面改这个） | **平铺**：`activity_hours` 在顶层 | 宿主界面 |
| `~/.wb-switch/gateway/gateway_native_config.json` | **网关** | **嵌套**：`schedule.activity_hours` | 宿主 `gateway.rs::write_native_config` 翻译生成 |

宿主负责把前者翻译成后者（`crates/ai-gateway-core/src/modules/gateway.rs` 的
`json!({ ..., "schedule": { "activity_hours": ..., ... } })`）。

⇒ **你在界面上改时点是生效的**，只是不直接落在网关读的那个文件里。
排障时若只打开 `gateway_config.json` 找 `schedule` 段，会得出
「配置根本没写进去 = 功能坏了」的**错误**结论。

⚠ 更隐蔽的一层：`Config.schedule` 是**普通嵌套字段**（`config.rs:173`），
**没有 `#[serde(flatten)]`**。所以若直接把 `activity_hours` 平铺写进网关的配置，
`serde` 会**静默忽略**它 —— 不报错、不打日志、字段拿默认值。
我第一次实验就是这么写的，结果 15:00 整点**没有触发**，差点误判成「排程是坏的」。
**判别办法**：网关启动时若有排程相关日志，看它用的是哪个文件；
或直接 `grep '"schedule"' gateway_native_config.json` 确认嵌套段存在。

### 陷阱二：启动补跑有 30 分钟窗口，容易和「到点触发」混淆

`Scheduler::run()` 做的第一件事不是等到点，而是 `run_startup_catch_up`：

```text
within_catch_up(now, last_scheduled_at(now, hours))
  ⇔ 计划时点 ≤ now  且  now − 时点 ≤ STARTUP_CATCH_UP_GRACE（30 分钟）
```

所以「网关重启后某个任务突然自己跑了」有两种可能：**到点触发** 或 **启动补跑**。
不区分就会得出矛盾结论（我第一次实验设 `hours=[当前小时]` 却因为超窗而没补跑，
误以为「排程根本没工作」；实际上当时距离整点已 57 分钟 > 30 分钟窗口）。

窗口存在的理由：网关在计划时刻前后重启、或机器从休眠唤醒时，不应直接等到第二天。
只补最近一轮，不会把多天的任务堆成风暴。

### 陷阱三：「自动跑」与「手动能跑」是两条独立路径

本次上下文里连着三个缺陷，症状都表现为「养号任务不好用」，但**层次完全不同**：

| 缺陷 | 影响范围 | 根因位置 |
|---|---|---|
| 未勾选账号不进池 | 自动 + 手动都不行 | 宿主导出过滤 |
| `account.id` 传成 `id` 而非 `uid` | **只有手动**（八个菜单入口） | 前端调用点 |
| 校园日活动已下线 | 只有校园日 | 上游不再下发该任务码 |

**自动触发完全不经过前端**（排程循环 → `run_care_task` → 直接跑），
因此第二类缺陷对它**毫无影响**。

⇒ 推论（本次实际用上的）：如果观察到「某任务从没自动跑过」，
那是一个**独立于**「手动点报错」的新问题，不要把两者混在一起查。

## Decision

把上述机制记录下来，不改代码（本篇是**核实既有行为**，不是引入新决定）。

### 自动触发的事实清单（全部实测/源码核实）

`next_wake` 是「到点该跑什么」的**唯一真相来源**
（`scheduler/mod.rs:831`）。到点执行的任务：

| 任务 | 默认时点 | 备注 |
|---|---|---|
| 签到 | `[9, 21]` | 搭猫猫旅行便车 |
| 保活 | `[22]` | 另有「距上次成功 ≥24h」的启动兜底 |
| 活跃上报 | `[10]` | |
| 夜猫子 | `[1]` | |
| 开学季 | `[12]` | |
| trial | `[9, 21]` | 国际版专属 |
| Qoder 领取 | 由 `qoder_claim_hours` 给，**不兜底** | 空 ⇒ 不产生时点 |
| **活跃地图** | **跟随活跃上报**（同一时点） | 曾经只有手动入口，已修 |

⚠ `GrowthMap` 那条值得记：代码里有一段注释写着「之前只有手动入口、没有 slot，
因此用户不点按钮就永远不会执行」——**这是本仓库已经发生过一次的同型缺陷**。
新增任务时若只加手动入口不加入 `next_wake`，就会静默地永不自动执行。

### 验证方法（可复现，且不会被陷阱误导）

隔离实例（独立端口 / 独立 `auth_dir` / 独立 `state_file`），
配置**嵌套** `schedule`，把 `activity_hours` 设为**当前小时**：

```json
{ "schedule": { "activity_enabled": true, "activity_hours": [<当前小时>] } }
```

启动后观察日志（不需要点任何按钮）：

```text
15:04:51  activity <uid>: reported 3/3 ok
```

⚠ 判据是「**有没有跑**」，不是「跑成功」——把 `WB2A_CHAT_BASE_CN` 指向
`127.0.0.1:1` 制造传输层失败，`reported 3/3 ok` 仍会出现（动作已发出），
而后续的 `WARN` 只是收不到响应。反过来若指向上游真实域名，一次误判
「没触发」可能只是网络问题。

### 与本仓所有者机器的对照

`gateway_native_config.json` 的 `schedule` 段（本机实测）：七项开关全 `true`，
时点齐全（签到 9/21、活跃 10、夜猫子 1、开学季 12、trial 9/21、保活 22、
Qoder 10/21）。日志中可见自动触发的实证：
`10:01:36` / `13:59:32` / `14:51:15` 的「成长任务中心：排程触发」，
以及 `09:00:25` 的 trial 执行（正好是 `hours=[9,21]` 的 9 点）。

## Alternatives considered

- **不记笔记** — 它最强的理由是：这属于「既有行为」，而笔记规范的红线清单明确把
  「不改行为的说明」划在必须记录之外；而且它并不改变任何代码路径。
  否掉的原因是陷阱一和陷阱二都属于**「读代码会读错」**的那一类：
  双配置文件在同一个目录、同样叫「配置」，而嵌套结构被 `serde` 静默忽略
  **不产生任何日志**。这类事实无法从任一文件读出来——它存在于**两者之间的关系**里，
  只能靠实测记录。这正是笔记规范说的「代码说不出来的意图与边界」。

- **把这些内容并进「八个入口报不在账号池内」那篇 bug-fix** — 它最强的理由是
  **同一个排查过程里发现的**，合并能减少文件数，且那篇已经提到「自动触发不受影响」。
  否掉的原因是两者的**生命周期不同**：那篇记的是一个已修复的缺陷（有明确的
  根因、修法、故障注入）；本篇记的是**不会变的运行机制**。把机制塞进缺陷笔记，
  将来那篇被归档时机制就跟着丢了。规范也要求「一个事实只在一处讲透」。

## Consequences

- **收益**：下次验证「自动触发是否工作」时，不会再因配置结构或补跑窗口而误判。
- **收益**：把「自动跑 ≠ 手动能跑」写成显式判断，避免把不同层次的缺陷混查。
- **代价**：多一篇笔记（26 → 27）。
- **代价（真实）**：本篇记录的是**当前实现**，若 `next_wake` 的任务集合变化，
  需要回来更新那张表。**信号**：新增养号任务却没加入 `next_wake` 时，
  应同时更新本篇与 `GrowthMap` 那条注释所描述的教训。
- **已知上限**：本篇只覆盖「何时触发」。**触发后是否成功**取决于上游，
  那是另一条链路（本次多处 `WARN` 即属此类），两者不要混谈。

| 配置结构 | 网关读 `gateway_native_config.json`（嵌套 `schedule`），宿主读 `gateway_config.json`（平铺） |
| 本机真实配置 | 七项开关全 `true`，时点齐全 |
| 自动触发实证 | 日志中 10:01:36 / 13:59:32 / 14:51:15「成长任务中心：排程触发」，09:00:25 trial |
| 业主服务 | 全程未触碰 |

⚠ 本次踩了两个假结论，都已在上文写成陷阱：① 第一次实验把配置平铺，
15:00 未触发，差点判成「排程坏了」；② 第一次复现「不在账号池内」时
