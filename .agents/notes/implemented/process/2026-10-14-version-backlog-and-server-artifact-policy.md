# Agent Note: 版本积压与「服务端单文件产物不随 Release 发布」的口径

Status: implemented

## Problem

原 `docs/DECISIONS.md` D15（从 DECISIONS.md 迁移）。

两件**相互独立**的事被混在一起，产生了一个假问题：
「服务端产物没发 Release，是不是漏了 tag？」

- **tag 缺口**：1.0.39 ~ 1.0.46 未打 tag、未发 Release（安装包都已产出并落在 `dist\`，
  只差推 tag + 发 Release）。已发布的 Release 到 **v1.0.38** 为止。
- **产物口径**：服务端单文件产物（`dist\ai-gateway_<版本>_server-x64.exe`）
  历来**手工产出**，`release.yml` 没有它的构建步骤 ⇒ 它**不随 Release 发布**，
  因此**不需要**为它单独打 tag。

混在一起就会得出「漏了 tag」这个错误结论。答案是**不是** —— 两件事无关。

### 为什么 tag 缺口能长期存在而不被发现（值得记的教训）

- **发版一直是手工做的** ⇒ 流水线红不红没人看
- 更早的一个同型缺陷：`ci` 与 `release` 两条工作流**从 v1.0.23 起一直红**，
  `release.yml` 的 preflight 挂在「核心单测」⇒ 四平台 build 与「发布 Release」
  两步**全被 skip**，**等于 tag 打上去什么都不会发生**。
  根因之一是被 gitignore 的 `test-bin/` 在 CI 上不存在（夹具指向它），
  另一个是平台 / 环境变量假设（`#[cfg(windows)]`、`C:\...` 路径、`LANG`/`TZ`）。
- **教训**：`test-bin/`、`dist/` 这类被 gitignore 的目录，会让
  「**本地全绿 / CI 全红**」长期共存而不自知。
  凡是被 `.gitignore` 排除、但**测试或构建依赖**的路径，
  都必须先问一句「**CI 上它从哪来**」。

## Decision

两件事**分开记、分开处理**：

1. **tag 缺口** —— 补发 tag + Release 才能恢复版本信号。
2. **服务端单文件产物** —— 靠**文件名里的版本号**与 `ai-gateway.exe version` 自证
   （PE 版本资源**全空**）。

### 2026-10-16 修订：上面两条的原始前提均已失效

| 原前提 | 现状 |
|---|---|
| 1.0.39~1.0.46 未打 tag | **已补发**。`v1.0.46` 打在 `main`，Release 已发布，`releases/latest` 不再指向 v1.0.38 |
| server 单文件不随 Release 发布 | **已改为随 Release 发布**。`release.yml` 的 Windows 腿新增「构建纯部署版」步骤，产出 `ai-gateway_<版本>_server-x64.exe` + `.sha256`，与桌面版产物一并上传 |

⇒ 原文「翻案条件」的第 2 条已经触发，**那就是这次做的事**。
部署步骤见 `docs/SERVER-DEPLOY-1.0.46.md`。

⚠ 这条修订**不是**把结论改写成反面，而是「原结论成立过的那个前提消失了」。
原结论（两件事相互独立）**仍然成立**，只是第 2 件事的处理方式变了。

## Alternatives considered

- **把「不发 tag」当成省事** — 它最强的理由是**减少发布动作**：tag 与 Release 都是
  手工步骤，不发就能少一次出错机会，而安装包已经落在 `dist\` 里，需要的人拿得到。
  否掉的原因是 Release 是**唯一**的对外版本信号 —— 不发等于用户永远停在 v1.0.38，
  且自动更新（若仓库公开）会一直认为「已是最新」。

- **为服务端产物也打 tag** — 它最强的理由是**统一口径**：所有产物都有 tag，
  不必记「哪个随 Release、哪个不随」，也便于追溯「这个 exe 对应哪次提交」。
  否掉的原因是它会与桌面版 tag 语义冲突（一个 tag 对应两个不同产物），
  且该产物从来不在 Release 通道上 —— 给它打 tag 只是让 tag 列表变长，
  不会让任何人更容易找到它。

## Consequences

- **收益**：口径分开后，「漏 tag 了吗」这个问题有确定答案，不会每次发版重问一遍。
- **收益**：「被 gitignore 但测试/构建依赖的路径，先问 CI 上它从哪来」这条教训
  是可复用的 —— 它解释了整整 20 多个版本的假红。
- **代价与已知上限**：服务端产物靠**文件名**自证版本，PE 版本资源为空 ⇒
  改名或重命名后无法自证。**信号**：若将来需要「双击属性就能看到版本」，
  得给 PE 加版本资源，那时这条口径要重写。
- **代价**：`release.yml` 与 `ci.yml` 曾经「一直红」而不被察觉，说明
  **门禁的可见性**本身是个薄弱点 —— 手工发版流程下，红的流水线没人看。

## Verification

- `release.yml` 的 Windows 腿应产出 `ai-gateway_<版本>_server-x64.exe` + `.sha256`。
- `releases/latest` 应指向最新 tag（当前 `v1.0.46`）。
- 服务端产物自证：`ai-gateway.exe version`。
- 教训的可复现性：`git ls-files test-bin` 返回空（该目录不入库），
  而测试夹具曾指向它 —— 这正是「本地全绿 / CI 全红」的机制。
